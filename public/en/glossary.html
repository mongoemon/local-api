Performance Testing Glossary

This page collects terms commonly encountered in performance testing, with clear explanations and short examples.
Term Definition
Throughput The number of requests the system successfully responds to within a given time period. Typically measured in requests per second (RPS) or transactions per second (TPS).
Counted as completed requests / transactions, not individual internal steps or processes within the system.
Examples:
  • If throughput = 120 RPS, the system successfully handled 120 requests in one second.
  • If an API performs 3 internal steps (e.g., read DB, write log, send response) but completes the full request, it counts as 1 request — not 3.
  • If the system completed 900 requests over 10 seconds, throughput = 90 RPS.
Latency The time from when a request is initiated until the first byte of a response begins to arrive. Typically observed as p50/p95/p99 values.
Response Time The total time the system takes to fully respond to a request, from receipt to completion. Usually measured as median, p95, or p99.
Concurrency The number of requests being processed simultaneously in the system or within a thread group at a given moment.
Ramp-up The time taken to gradually increase the number of users or requests to the target load level, simulating a realistic traffic build-up.
Ramp-down The time taken to gradually reduce the number of users or requests after a test completes, allowing the system to return to a normal state gracefully.
Spike Test A sudden, short-duration increase in load to observe how the system responds and how quickly it recovers.
Stress Test A test that pushes the system beyond its normal operating capacity to identify failure points, overload handling behavior, and recovery characteristics.
Soak Test A test that applies a sustained, constant load over an extended period to check for memory leaks, resource exhaustion, and long-term stability.
Load Test A test that applies the expected real-world load to verify that SLA/SLO targets are met under normal operating conditions.
Bottleneck The part of the system that limits overall throughput or causes elevated latency — for example, CPU, memory, disk I/O, or the database.
SLA Service Level Agreement — a business-level commitment about the quality of service, such as p95 < 200ms or 99.9% availability.
SLO Service Level Objective — a technical target set to meet the SLA, covering metrics such as response time, error rate, and availability.
Error Rate The percentage of requests that failed relative to the total number of requests. Failures include 4xx/5xx responses, timeouts, and assertion failures.
Note: A slow response is not an error. If the response is 2xx and passes all assertions, it is considered successful.
Time to First Byte (TTFB) The time elapsed from when a request is sent until the client receives the first byte of the response.
Warm-up A period that allows the system to reach a steady operating state before measurement begins — for example, loading caches or opening connection pools.
Think Time A pause between requests in a simulated user session, used to mimic real user behavior.
CPU Saturation A state in which the CPU is fully utilized and can no longer accept additional requests.
Uptime The length of time a system or service has been running continuously without interruption. For example, a server running without a restart for 7 days has an uptime of 7 days.
PID Process ID — a unique identifier assigned to a running process by the operating system. Used to monitor processes, collect logs, or terminate them.
Memory Leak A condition in which the system fails to release memory after use, causing memory usage to grow continuously until a crash or out-of-memory (OOM) error occurs.
Throughput Ceiling The maximum throughput level a system can sustain before errors appear or latency spikes.
p90 / p95 / p99 Percentile values of response time. p90 means 90% of requests completed faster than this value; p95 means 95%; p99 means 99%.
Example: If p95 = 200ms, then 95% of all requests responded in under 200ms, while the slowest 5% may have taken longer.
Thread Group A group of simulated users in JMeter that defines the number of threads, ramp-up time, and loop count.
Sampler A component that sends requests — such as HTTP Request, JDBC Request, or FTP Request — to simulate real requests the system will receive.
Listener A component that collects and displays test results — for example, Aggregate Report, Summary Report, or View Results Tree.
Assertion A validation rule applied to a response — for example, checking that the response code is 200 or that the body contains expected content.
Timer Adds a delay between requests to simulate real user wait time.
Config Element Stores shared settings such as HTTP Header Manager or CSV Data Set Config for reuse across multiple samplers.
PreProcessor / PostProcessor Scripts or transformations applied before or after a request is sent — for example, extracting a token or transforming data from a response.

Metric SLA

In performance testing, the primary metrics used as SLA criteria are:

  • p90 / p95 / p99 - percentile response time values
  • Error rate - percentage of failed requests
  • Throughput - number of requests per second the system can handle
  • Availability - percentage of time the system is operational and reachable
  • CPU utilization - percentage of CPU used during the test
  • Memory usage - amount of memory consumed by the system during the test
  • TTFB - time until the first byte is returned to the client

Example SLA Formats

Metric Example SLA Description Example Result
p90 < 150ms 90% of requests must complete within this value Result = 132ms → Pass
p95 < 200ms 95% of requests must complete within this value Result = 215ms → Fail
p99 < 300ms 99% of requests must complete within this value Result = 280ms → Pass
Error rate < 1% No more than 1% of requests may fail Result = 0.8% → Pass
Throughput >= 120 RPS The system must handle at least 120 requests per second Result = 145 RPS → Pass
Availability >= 99.9% The system must be available for more than 99.9% of the test duration Result = 99.95% → Pass
CPU utilization < 80% CPU must not reach saturation during the test Result = 76% → Pass
Memory usage < 70% of available RAM Memory usage must not exceed the level that would trigger GC pressure or failure Result = 55% → Pass
TTFB < 100ms Time to first byte must not exceed this threshold Result = 88ms → Pass

p90 / p95 / p99 in JMeter

In JMeter, p90/p95/p99 values are visible in listeners such as Aggregate Report or Summary Report, which display percentile values directly.

  • Aggregate Report: Provides columns for 90%, 95%, and 99% showing response time at each percentile.
  • Summary Report: Displays 90%, 95%, and 99% similarly and is well-suited for a high-level test overview.
  • View Results in Table: Shows the response of each individual sample, but percentile values must be read from an aggregating listener.

Example usage:

1) Add a Thread Group and HTTP Request sampler
2) Add an Aggregate Report listener
3) Run the test
4) Read the values in the 90%, 95%, and 99% columns

Common JMeter listeners

  • Aggregate Report - View a summary of averages, median, percentiles, throughput, and error rate
  • Summary Report - A simplified results summary suitable for a high-level overview
  • View Results in Table - Inspect per-sample details, but not suitable for reading long percentile sequences
  • View Results Tree - Examine individual request/response pairs when debugging a script or an assertion

How to Read Results from a Listener

  • Check 90%, 95%, and 99% to see whether they meet the SLA
  • If p95 fails but p90 passes, the slowest 5% of requests are creating the problem
  • If p99 is well above the SLA value, the slowest 1% have an issue — possibly a bug in a specific path
  • If Error rate > 1%, too many requests are failing, even if latency still looks acceptable.
    JMeter counts as an error when the response code is 4xx/5xx, a timeout occurs, or an assertion fails.
    Not an error when the response succeeds (2xx) but latency is higher than the SLA value.
  • Use Throughput to determine whether the system still has headroom for more load

If 95% is significantly above the SLA value, the slowest 5% of requests are causing some users to experience slow performance — investigate the bottleneck further.

Example Results After a Test Run

Assume the following SLA:

  • p90 < 150ms
  • p95 < 200ms
  • p99 < 300ms
  • Error rate < 1%
Metric Actual Result Status Description
p90 132ms Pass 90% of requests responded faster than 132ms
p95 215ms Fail Must be under 200ms, but the slowest 5% took 215ms
p99 280ms Pass 99% of requests responded faster than 280ms
Error rate 0.8% Pass Below the 1% threshold

This example shows that overall performance is acceptable, but the root cause of the slowest 5% of requests (p95 fail) needs further investigation.

JMeter listeners such as Aggregate Report report these values in the 90%, 95%, and 99% columns, enabling direct comparison against your SLA.
