Test Types And Thread Groups

This page explains how to choose a test type, pair it with the right thread group, configure it correctly, and interpret results against customer-defined SLAs.

Step 1: Choose a Test Type That Matches Your SLA

Before running a test, you need to know what the SLA is addressing — because each test type answers a different question.
Test TypeUse When the SLA Refers ToQuestion It AnswersExample Criterion
Load Test normal traffic, expected users, baseline performance Does the system meet the SLA under realistic load? p95 < 800ms at 20 users
Stress Test capacity, breaking point, graceful degradation At what level does the system start to degrade or fail? System remains stable up to 80 concurrent users
Spike Test traffic surge, flash sale, peak event, recovery time Can the system handle a sudden load spike, and how quickly does it recover? 3x traffic within 1 minute, recovery within 2 minutes
Endurance Test stability, continuous operation, memory drift Does the SLA hold steady or drift when running for many hours? p95 < 900ms sustained over 8 hours

Step 2: Choose a Thread Group That Fits Your Test Type

Thread GroupSuitable ForControlsChoose When
Normal Load, Endurance Thread count, ramp-up, loop count Getting started, functional checks, baselines, straightforward load tests
Concurrency Stress, Spike, Load Number of concurrently active users You need to know how many simultaneous sessions the system can support
Stepping Stress, Spike Adds threads in incremental steps over time You want to find a breaking point or observe step-by-step degradation
Arrival Rate Load, Endurance Request rate per second (RPS/TPS) You want to control throughput rate rather than user count

Step 3: JMeter Thread Group Configuration Cheat Sheet

The values below are starting points — adjust them based on the load specified by the customer.

Normal Thread Group — Load Test

Thread Group
  Number of Threads (users):  10–20
  Ramp-Up Period (seconds):   30
  Loop Count:                 20
  Duration (seconds):         — (use loop count instead)

Use for: baseline, functional load, basic load test

Concurrency Thread Group — Stress Test

Concurrency Thread Group (requires bzm plugin)
  Target Concurrency:   start at 10, increase to 80+
  Ramp-Up Time (sec):   60
  Ramp-Up Steps:        5
  Hold Target Rate:     120 seconds

Use for: stress test, finding saturation point, checking active sessions

Stepping Thread Group — Spike / Threshold

Stepping Thread Group (requires plugin)
  Start Threads Count:       5
  Initial Delay (sec):       0
  Start users count:         5
  Start users period (sec):  30
  End Threads Count:         100

Use for: spike test, finding breaking point step-by-step

Arrival Rate Thread Group — Steady Traffic

Arrivals Thread Group (requires bzm plugin)
  Target Rate (requests/sec): 50
  Ramp-Up Time (sec):         30
  Ramp-Up Steps:              3
  Hold Target Rate (sec):     120

Use for: controlling RPS, open workload simulation, endurance at a fixed rate

In real-world testing, you need to measure multiple layers simultaneously — not just response time alone.

Step 7: Suggested Run Order for Beginners

Round 1 — Baseline (1 user)

Verify that the flow works correctly before adding any load.

  • 1 thread, 1 loop, no ramp-up
  • Open View Results Tree to inspect actual request/response pairs
  • Every step must return 200 and the variable chain must be correct
  • Fix any errors before proceeding — do not run the next round until baseline passes

Round 2 — Load Test (expected load)

Test at the normal load specified by the customer to validate the primary SLA.

  • Normal Thread Group: 10–20 threads, ramp-up 30s, loop 20
  • Open Aggregate Report to review p90/p95/p99
  • Compare against the SLA: p95, error rate, traffic mix
  • If it passes, proceed to stress test; if not, investigate the bottleneck first

Round 3 — Stress Test (push to limit)

Find the point at which the system begins to degrade by progressively increasing load.

  • Concurrency Thread Group: increase from 20 → 40 → 80 → 120 users
  • Monitor error rate and p95 at each step
  • Record the point where errors first appear or latency breaches the SLA
  • That point is the breaking point / capacity threshold

Round 4 — Spike Test (burst)

Simulate a sudden load surge to observe recovery behavior.

  • Stepping Thread Group: ramp from 5 → 100 threads within 30 seconds
  • Watch for error bursts and measure recovery time after the spike subsides
  • If the customer specifies "must recover within 2 minutes," check the timestamps

Round 5 — Endurance Test (long run)

Run at expected load for an extended period to observe drift and memory behavior.

  • Normal Thread Group: 10 threads, duration 1–8 hours
  • Compare p95 at the start vs. the end — if it keeps climbing, there is likely a leak
  • Keep GET /status and GET /metrics open to monitor runtime values during the run

Quick Reference: Test Type → Thread Group → SLA Metric

Test TypeRecommended Thread GroupPrimary Metric To CheckPass Condition Example
Load Normal or Arrival Rate p95, error rate, traffic mix p95 < 800ms, error < 1%
Stress Concurrency or Stepping Point where errors first appear, p95 breach level System remains stable at 80 users
Spike Stepping or Concurrency error burst size, recovery time Recovers within 2 minutes after spike
Endurance Normal or Arrival Rate + Duration p95 drift from start to end of run p95 < 900ms sustained over 8 hours

Quick Guidance

  • Always start with Normal Thread Group if you are just getting started or need a baseline
  • Use Concurrency Thread Group to find the concurrent user limit
  • Use Stepping Thread Group to find a breaking point in incremental steps
  • Use Arrival Rate Thread Group to control the request rate (RPS)
  • Always check Error % before looking at latency — high error rates make latency figures meaningless
  • Focus on p95 in Aggregate Report, not the average
  • Use the parent sample of a Transaction Controller for SLA measured as a user journey
  • Keep GET /status open during the run to monitor activeRequests and confirm the server has not crashed
