Performance Testing Lab

Performance Testing Lab is a local API for safely learning load testing and performance monitoring on your own machine.

New here? Start from this page and follow each step in order. Take your time — working through one thing at a time leads to faster understanding.

🗺️ Learning Path (Start Here)

Step 1 — Understand what this API does (5 minutes)

Read the Endpoint Purpose table below to learn what each endpoint is designed to test. For example, /fast measures baseline latency, /busy hits the concurrency limit, and /demo/* simulates an e-commerce flow.

Step 2 — Try calling endpoints in the browser (5–10 minutes)

Click the links in Try These Endpoints below to see real responses from each endpoint before starting with JMeter.

Step 3 — Learn the demo transaction flow

Open the Demo Learning Path and try calling the full e-commerce flow: context → search → add to cart → checkout → order status.

Step 4 — Build a JMeter test plan

Open the JMeter Guide and follow the steps in order: set HTTP Request Defaults → create a Thread Group → add a Transaction Controller → configure JSON Extractors.

Step 5 — Choose a test type and thread group

Open Test Types to decide whether to run a load, stress, spike, or endurance test, and which thread group configuration to use.

Step 6 — Practice with real exercises

Open Assignment and work through the tasks, from foundational exercises up to full performance testing scenarios.

🔗 Try These Endpoints (Step 2)

Click a link to call an endpoint and see the real response — GET endpoints are clickable immediately; POST endpoints require Postman or curl.

  • /fast — baseline, responds immediately
  • /slow — adds a 200 ms delay
  • /busy — adds a 3000 ms delay, used to hit the concurrency limit
  • /cpu — CPU workload
  • /memory — memory allocation
  • /io?mode=read — reads a file from disk
  • /io?mode=write — writes a file to disk
  • /prep — generates a token seed for use with /protected
  • GET /protected — requires a token; try via Postman
  • /error — simulates a 500 error
  • /status — runtime info
  • /metrics — Prometheus metrics
  • POST /auth/login — receive a JWT token (use Postman)
  • POST /auth/verify — verify a JWT token
  • POST /submit-one — test body validation (1 field)
  • POST /submit-two — test body validation (2 fields)
  • POST /cleanup — delete temporary files created by /io

Demo endpoints: /demo/context · /demo/dashboard · /demo/search?q=mouse · /demo/product/details?productId=sku-101

Gold standard on this page refers to the target baseline for APIs in this lab — not a universal SLA for all production systems. Adjust targets based on business criticality and your actual infrastructure.

📘 Endpoint Purpose And SLA (Step 3)

Endpoint What It Tests Gold Standard / Recommended SLA
/fast Baseline endpoint — measures minimum system latency when the server has almost no work to do p95 < 100 ms, error rate < 1%
/slow Simulates a fixed downstream latency — observe timeout behavior, queueing, and latency budget p95 < 300 ms (including the configured delay), error < 1%
/busy Forces high in-flight requests until the concurrency limit is hit, triggering 503 backpressure No user-facing SLA — used to confirm backpressure is working correctly
/cpu CPU saturation and event-loop blocking p95 should not spike high enough to affect other endpoints; 5xx < 2%
/memory Memory pressure, GC pauses, and OOM risk Process memory should not grow continuously; error rate < 1%
/prep Generates a seed for JMeter pre-processors — requestId, token, authorizationHeader Fast, consistent response with no heavy workload
/protected Tests the auth header flow — accepts Authorization: Bearer ... and x-access-token 200 with valid token, 401 with no token, 403 with invalid token
/io?mode=read|write I/O bottleneck from real file reads/writes in tmp/ Check durationMs in the response — use to observe disk throughput
POST /cleanup Removes temporary files after /io — intended for use in a tearDown Thread Group Always returns 200, even when there are no files to delete
POST /submit-one Request body validation — requires 1 field: name 200 when all fields present, 400 when field is missing
POST /submit-two Request body validation — requires 2 fields: name and type 200 when all fields present, 400 when a field is missing
/error Intentionally simulates HTTP 500 — used to test error handling, retries, and alerting Not a gold endpoint — should always return 500
/status Runtime health check — pid, startedAt, uptimeSec, activeRequests Returns 200 at all times while the process is running
/metrics Prometheus scrape endpoint — throughput, latency, request counts Stable; must not slow down other requests
POST /auth/login JWT authentication — send username/password to receive a JWT token valid for 24 hours 200 with correct credentials, 401 with wrong credentials, error < 1%
POST /auth/verify Verify a JWT token — send Authorization: Bearer <token> 200 for valid token, 401 for expired token, 403 for invalid token

🔥 How To Trigger Each Scenario

GoalEndpointRecommended SettingsExpected Outcome
Measure baseline latency /fast 10–50 users, ramp-up 1–5 sec Almost all 200s with low latency
Observe fixed latency /slow 50–100 users, SLOW_DELAY_MS=200–1000 200 responses but response time rises with the delay
Hit the concurrency limit /busy 100–300 users, MAX_CONCURRENT=20–50, BUSY_DELAY_MS=3000 Some requests get 200, some get 503
Observe CPU bottleneck /cpu 20–100 users, CPU_ITERATIONS=10M–100M 200 responses but high latency; other endpoints slow down as well
Observe memory pressure /memory 20–100 users, MEMORY_ARRAY_SIZE=1M–5M Variable response times, elevated memory usage
Test auth header flow /protected 1–50 users, header Authorization: Bearer lab-token 200 with valid token, 401 with no token, 403 with invalid token
Observe I/O bottleneck /io?mode=read|write 20–100 users, IO_FILE_SIZE_KB=1024–8192 durationMs rises with file size
Test body validation POST /submit-one, /submit-two Send correct and incorrect JSON bodies 200 when complete, 400 when a field is missing
Test the 5xx path /error 1–50 users 500 on every request
Clean up temp data POST /cleanup 1 user in a tearDown Thread Group 200 with a list of cleaned files

💬 Response Meanings

  • /fast → { "message": "fast response" } — endpoint has no workload; responds immediately
  • /slow → slow response (Xms) — server delays according to SLOW_DELAY_MS
  • /busy → busy response (Xms) if the request gets through; 503 Server too busy (plain text) if the limit is hit
  • /cpu → result is the loop sum, iterations is the iteration count
  • /memory → size is the number of elements successfully allocated
  • /prep → contains token, authorizationHeader, requestId, timestamp
  • /protected → authenticated: true with a valid token; missing_token or invalid_token otherwise
  • /io → mode, fileSizeKb, durationMs
  • POST /cleanup → cleaned list of deleted files, cleanedCount
  • POST /submit-one → received one required parameter or missing_required_parameter
  • POST /submit-two → received two required parameters or missing_required_parameters
  • /error → intentional server error — always responds with 500
  • /status → running: true, pid, startedAt, uptimeSec, activeRequests
  • /metrics → Prometheus text format, not JSON
  • POST /auth/login → token (JWT string) when credentials are correct
  • POST /auth/verify → valid: true, decoded with a valid token; token_expired or invalid_token otherwise

📏 SLA Interpretation

  • Look at p95 or p99 rather than the average — percentiles reflect real user experience when the system is under load
  • Error rate — if 5xx responses or timeouts exceed 1% on a primary endpoint, the system is failing its threshold
  • Availability — for /status, target 99.9% or higher
  • Isolation — if loading /cpu causes /fast to breach its SLA, the workloads are not sufficiently resource-isolated
