Assignment for Beginners

This page is a set of exercises for beginners, designed to let you try each part of the API one at a time and see answers immediately. It is ideal for practising writing requests, reading responses, and understanding the purpose of each endpoint.

How to use

  • Read the prompt in each section first.
  • Try calling the endpoint using a browser, Postman, or curl.
  • Read the answer below each task to verify your result.
Before you begin, review the JMeter Guide for setting up Thread Groups, Variables, and Extractors, and Test Types for selecting the right test type and run order.

Task 1: Call the baseline endpoint

Prompt

Call GET /fast and verify what message is returned in the response.

Steps
  • Use a browser, curl, or Postman to open http://localhost:3001/fast.
  • For a baseline test, start with 1 thread or a single request.
  • Confirm that the response is JSON and contains a message field.
  • Verify that the message value is fast response.
Answer

The correct response will be JSON:

{
  "message": "fast response"
}

If you receive this response, the server is running and the baseline endpoint is responding normally.

Task 2: Test the delay endpoint

Prompt

Call GET /slow and observe the time taken for the request and the message in the response.

Steps
  • Use curl or Postman to call http://localhost:3001/slow.
  • Start with 1–2 threads or 1–2 concurrent requests to observe the delay clearly.
  • Note the elapsed time from sending the request to receiving the response.
  • Check that the response message indicates the delay, e.g., slow response (200ms).
Answer

The response will be JSON similar to:

{
  "message": "slow response (200ms)"
}

The number after "slow response" comes from the config.workloads.slowDelayMs setting in the system.

Task 3: Verify the legacy auth flow

Prompt

Call GET /prep to see the token and authorization header provided by the system, then call GET /protected with the header Authorization: Bearer lab-token.

Steps
  • Open GET http://localhost:3001/prep and check that the response contains the token and authorizationHeader fields.
  • Use the value lab-token in the Authorization: Bearer lab-token header when calling /protected.
  • Primarily test with 1 request, but use 2–3 threads concurrently if you want to observe concurrent behavior.
  • Verify that the response grants access to the protected resource.
Answer

The response from /prep will include a token field and an authorizationHeader field; the token value is normally lab-token.

When calling /protected with the following header:

Authorization: Bearer lab-token

The correct response will be:

{
  "message": "protected resource access granted",
  "authenticated": true,
  "tokenSource": "authorization"
}

Task 4: Try JWT-based auth

Prompt

Use POST /auth/login with the following JSON body:

{
  "username": "demo",
  "password": "password"
}

Then take the token from the response and call POST /auth/verify with the header Authorization: Bearer <token>.

Steps
  • Send a POST to http://localhost:3001/auth/login with the specified body.
  • Copy the token value from the response.
  • Send another POST to http://localhost:3001/auth/verify with the header Authorization: Bearer <token>.
  • Test with 1–2 concurrent requests to confirm the token remains valid under concurrent use.
  • Verify that the response contains valid: true and that the decoded data matches the user.
Answer

The response from /auth/login will be JSON containing a token field, for example:

{
  "message": "login successful",
  "authenticated": true,
  "token": "eyJhbGciOiJIUzI1NiIs..."
}

Using that token to call POST /auth/verify will return a response similar to:

{
  "message": "token is valid",
  "valid": true,
  "decoded": {
    "userId": "user-123",
    "username": "demo",
    "iat": "...",
    "exp": "..."
  }
}

Task 5: Test a validation error

Prompt

Call POST /submit-one without sending a body, or with an empty body, and observe how the system responds.

Steps
  • Use curl or Postman to send a POST to http://localhost:3001/submit-one without a body.
  • Use 1–3 concurrent requests to confirm that validation works across multiple requests.
  • Check that the response is HTTP 400 or contains a JSON error.
  • Try sending a valid body such as { "name": "test" } and compare the results.
Answer

The response will be HTTP 400 with JSON:

{
  "error": "missing_required_parameter",
  "required": ["name"]
}

If you send a valid body such as { "name": "test" }, you will receive:

{
  "message": "received one required parameter",
  "data": { "name": "test" }
}

Task 6: Try the I/O flow and cleanup

Prompt

Call GET /io?mode=write and GET /io?mode=read, then call POST /cleanup to delete the temporary files.

Steps
  • Call GET http://localhost:3001/io?mode=write to create a temporary file.
  • Call GET http://localhost:3001/io?mode=read to read data from the file.
  • For the I/O flow, try 1–2 concurrent requests to observe sequential behavior.
  • Call POST http://localhost:3001/cleanup to clear all temporary files.
  • Check each step's response to confirm it shows durationMs and the cleanup status.
Answer

Both /io?mode=write and /io?mode=read will return JSON containing durationMs and mode.

After that, POST /cleanup will return JSON such as:

{
  "message": "cleanup completed",
  "cleaned": ["io-test.dat"],
  "cleanedCount": 1
}
Once you have completed all 6 tasks, go back and read the Demo Flow to learn about more complex flows, and use your answers to design your own JMeter test plan.

Next-Level Exercises

Challenge 1: Compare /fast with /slow

Prompt

Call /fast and /slow, note the time taken for each request, and compare the difference.

Steps
  • Use a timing tool such as curl with timing flags or Postman to call both endpoints.
  • Record the latency values for /fast and /slow.
  • Compare the results to see how much they differ, and confirm that the delay matches the slowDelayMs config value.
Answer

You will see that /slow always takes longer than /fast, with the additional time matching the slowDelayMs configuration.

Challenge 2: Create an error case with /submit-two

Prompt

Call POST /submit-two with a body that is missing only the type field and observe the response.

Steps
  • Send a POST to http://localhost:3001/submit-two with a body such as { "name": "test" }.
  • Try 1–3 concurrent requests to verify that the validation error is consistent.
  • Check that the response code is 400 and that the response body lists the missing fields.
  • Try sending a complete body with both name and type and compare the results.
Answer

The response will be HTTP 400 and the JSON will contain:

{
  "error": "missing_required_parameters",
  "required": ["name", "type"]
}

Challenge 3: Test an invalid token

Prompt

Call POST /auth/verify with the header Authorization: Bearer invalid-token and observe the response.

Steps
  • Send a POST to http://localhost:3001/auth/verify with the header Authorization: Bearer invalid-token.
  • Try 1–2 requests to confirm that invalid tokens are rejected every time.
  • Check that the response code is 403 and that the response body shows an invalid token error.
  • Compare with a valid token obtained from /auth/login to see the difference.
Answer

The response will be HTTP 403 with JSON:

{
  "error": "invalid_token",
  "message": "Token is not valid"
}

Challenge 4: Basic metrics

Prompt

Call GET /metrics and look for the variable http_request_duration_seconds_count or other HTTP-request-related metrics.

Steps
  • Open GET http://localhost:3001/metrics in a browser or with curl.
  • Search for the string http_request_duration_seconds_count or similarly named metrics.
  • Observe that it is a Prometheus counter/histogram and understand how it is used to measure request duration.
Answer

You will find Prometheus-format text containing metric counts and histograms for request duration, which can be used to assess API performance.

Intermediate Assignment

Intermediate 1: Analyze /status at runtime

Prompt

Call GET /status and observe the values of activeRequests, uptimeSec, and pid when calling it multiple times.

Steps
  • Call GET http://localhost:3001/status multiple times at different intervals.
  • Repeat 2–3 requests per round to check the consistency of the values.
  • Record the values of pid, uptimeSec, and activeRequests.
  • Notice that pid stays constant, uptimeSec increases, and activeRequests may change with load.
Answer

You will see that pid remains constant throughout the session, uptimeSec increases over time, and activeRequests changes according to the number of requests currently being processed.

Intermediate 2: Compare /fast and /slow using /status

Prompt

Call GET /fast and GET /slow concurrently, then call GET /status to observe activeRequests and the server's responsiveness.

Steps
  • Open two tabs or two terminals: call /fast and /slow at the same time.
  • Start with 1–3 concurrent requests per endpoint.
  • Call GET /status at that moment and record activeRequests and uptimeSec.
  • Observe that the server continues to respond even while /slow takes longer.
Answer

While /slow is running, activeRequests may increase and uptimeSec continues to count up. This confirms that the system remains operational during periods of high latency.

Intermediate 3: Examine error cases with request rate

Prompt

Call POST /submit-two with a body missing the type field and observe the error response, including the response code and message.

Steps
  • Send multiple requests to /submit-two without the type field.
  • Start with 5–10 concurrent invalid requests to establish a basic error rate.
  • Verify that the response code is always 400 and the body shows the missing fields.
  • If possible, repeat multiple times to confirm that error behavior is consistent.
Answer

You will receive HTTP 400 and a JSON error with the missing_required_parameters field, confirming that the system correctly detects validation errors even under increased load.

Intermediate 4: Find histogram metrics from /metrics

Prompt

Call GET /metrics and look for a counter or histogram metric for response duration, such as http_request_duration_seconds_bucket.

Steps
  • Call GET http://localhost:3001/metrics and search for metric names containing the word bucket or count.
  • To populate the metrics with data, run 5–10 requests first and then fetch /metrics again.
  • Observe that histogram buckets contain latency ranges such as le="0.1" and le="0.5".
  • Check whether these metrics can be used to calculate percentiles.
Answer

If you find http_request_duration_seconds_bucket, it means the metric stores latency as a histogram and can be used to analyze percentiles.

Advanced Assignment

Advanced 1: Define an SLA and compare against real results

Prompt

Define an SLA such as p95 < 200ms and Error rate < 1%, then call GET /metrics or run multiple tests to determine whether the system meets the SLA.

Steps
  • Generate approximately 10–20 requests or 2–5 concurrent threads to produce visible metrics.
  • Call GET /metrics before and after running multiple requests.
  • Locate metrics that show histograms and error counts.
  • Compare the percentile values against the defined SLA, e.g., calculate p95 from the buckets.
  • Check whether the error rate is below 1%.
Answer

Review percentile values from the metric histograms and error counts. If p95 exceeds the SLA threshold or the error rate is above 1%, tuning or bottleneck resolution is required.

Advanced 2: Test recovery after high load

Prompt

Call /slow repeatedly to increase the load, record the activeRequests value, and check whether /status returns to normal after stopping requests.

Steps
  • Send 10–20 repeated requests to /slow, or use 3–5 concurrent threads.
  • Monitor /status during high load to observe activeRequests.
  • Stop sending requests, then call /status again to confirm that activeRequests drops and the server remains responsive.
Answer

After stopping /slow requests, activeRequests should decrease and the server should continue responding to /status normally, demonstrating that the system recovers successfully.

Advanced 3: Check token expiration / invalidation

Prompt

Use POST /auth/login to obtain a token, then call POST /auth/verify with the same token after a short wait to observe token validation behavior.

Steps
  • Send a POST to /auth/login to receive a token.
  • Use the same token to call /auth/verify with the header Authorization: Bearer <token>.
  • To test expiration, wait 10–30 seconds and try calling again.
  • To observe concurrency, try 2–3 verify requests simultaneously.
Answer

If the token is still valid, you will receive valid: true. If the system has a token expiration configured and it has elapsed, you may encounter invalid_token.

Advanced 4: Create and analyze an error spike

Prompt

Call POST /submit-two or /error repeatedly to drive the error rate up, then observe how /metrics and /status reflect changes in error rate and activeRequests.

Steps
  • Call POST /submit-two or /error 10–20 times, or use 5–10 concurrent invalid requests.
  • Call GET /metrics to check the error count and related metrics.
  • Call GET /status to confirm the system is still responding and to observe how activeRequests changes.
Answer

You should see the error count increase in metrics. If the error rate exceeds the SLA, service reliability may degrade even if uptime remains high.

Performance Testing Assignments

Load Testing: Test under normal load

Prompt

Create a JMeter test plan to call GET /fast and GET /slow under normal (expected) load, then analyze throughput, latency, and error rate.

Steps
  • Create a Thread Group in JMeter with 10–20 threads, a 30-second ramp-up, and a loop count of 5–10.
  • Add HTTP Request samplers for /fast and /slow.
  • Add a Response Assertion to verify response code 200 and the correct message.
  • Add an Aggregate Report listener to view average response time, throughput, and error %.
  • Run the test, then call GET /status and GET /metrics to check activeRequests and histogram metrics.
Answer

Load testing should show consistent throughput, latency below the SLA (e.g., p95 < 500ms), and an error rate < 1%. If throughput drops or latency increases, a bottleneck exists.

Stress Testing: Find the breaking point

Prompt

Progressively increase the load until the system starts to fail (the breaking point) by calling GET /slow and POST /submit-one, then observe when the error rate rises or response time degrades.

Steps
  • Start with a Thread Group of 20–50 threads, a 60-second ramp-up, and a duration of 5–10 minutes.
  • Add HTTP Requests for /slow and /submit-one with a valid body.
  • Use a Constant Timer of 1–2 seconds between requests to simulate user pacing.
  • Add listeners such as View Results Tree and Summary Report to monitor error trends.
  • Run the test and monitor /status every 30 seconds to track activeRequests and uptime.
Answer

Stress testing will reveal the breaking point when the error rate exceeds 5%, response times exceed 2–3 seconds, or the server becomes unresponsive. This point represents the system's maximum capacity.

Spike Testing: Test sudden load bursts

Prompt

Simulate a sudden load spike by calling GET /fast and GET /slow with a large number of concurrent requests over a short period, then check whether the system recovers.

Steps
  • Create a Thread Group with 50–100 threads, a very fast ramp-up of 10 seconds, and a loop count of 1–2.
  • Add HTTP Requests for /fast and /slow.
  • Use the Ultimate Thread Group or Step-Up Thread Group to create a spike pattern.
  • Add listeners to observe response time and error rate during the spike.
  • After the spike, call /status and /metrics to check recovery and error metrics.
Answer

Spike testing should show a temporary increase in latency during the spike, but the system should recover once the load subsides. If the error rate is high or the server crashes, auto-scaling or resource allocation adjustments are needed.

Endurance Testing: Long-duration test

Prompt

Run a test continuously for an extended period (hours) under normal load to check for memory leaks, resource exhaustion, or performance degradation over time.

Steps
  • Configure a Thread Group with 5–15 threads, a 30-second ramp-up, and a duration of 30–60 minutes or longer.
  • Add HTTP Requests for /fast, /slow, and /status (to use for monitoring).
  • Add Response Assertions and listeners to track performance trends over time.
  • Run the test and periodically monitor /status and /metrics to observe uptime, activeRequests, and memory usage.
  • Watch for degradation in response time or error rate as time passes.
Answer

Endurance testing will reveal issues such as memory leaks if response time increases or the error rate climbs over time. A well-performing system should maintain consistent performance throughout the entire duration.

Volume Testing: Test with large data volumes

Prompt

Test the system with large data volumes, such as sending requests with large bodies or calling endpoints that process large amounts of data, and observe how latency and throughput change.

Steps
  • Create a Thread Group with 5–10 threads, a 20-second ramp-up, and a loop count of 3–5.
  • Add an HTTP Request for POST /submit-one or /submit-two with a large body (e.g., a JSON array of 1,000 elements or a very long string).
  • Use CSV Data Set Config to feed large data from a file.
  • Add listeners to observe response time and error rate when dealing with large payloads.
  • Run the test and monitor /status for activeRequests and /metrics for memory or CPU metrics if available.
Answer

Volume testing will reveal whether the system handles large data well. If response time increases significantly or the error rate is high, data processing optimization or increased resource limits are needed.

Scalability Testing: Test scale-out behavior

Prompt

Test how system performance changes as users or resources are gradually increased, and identify the point at which performance no longer scales linearly.

Steps
  • Use the Step-Up Thread Group or Ultimate Thread Group to increase threads incrementally (e.g., start at 5 threads, then 10, 20, 50).
  • Set a duration of 2–5 minutes per step to allow the system to stabilize.
  • Add HTTP Requests for /fast and /slow, as well as /status for monitoring.
  • Add an Aggregate Report to view throughput and response time at each level.
  • Analyze whether throughput increases proportionally with threads and identify the point where performance plateaus or declines.
Answer

Scalability testing reveals how well the system scales. If throughput does not increase proportionally with the number of users, there is a bottleneck in the architecture or insufficient resources.
