Server Configuration

All changes take effect immediately — no server restart required. Use the presets to switch between a comfortable default state and a tight stress mode, or tune individual values for targeted testing.
Quick Presets:

Rate Limiting

Limits how many requests a client can make within a sliding time window. Returns 429 Too Many Requests when the count is exceeded. Disabled by default so you never hit a 429 during normal exploration. Enable it during load tests to observe error handling behavior.
Setting Value What it controls
Enabled
RATE_LIMIT_ENABLED
Default: off
 When on, every inbound request is counted per client IP within the window. Requests that exceed Max per Window receive 429 until the window resets.
On: enables rate enforcement — JMeter will produce 429s once threads × loops exceed the limit.
Off: no rate limiting regardless of request volume.
Window Duration
RATE_LIMIT_WINDOW_MS
Default: 60000 ms (1 min)
milliseconds
 How long one rate-limit window lasts. After this period, the request count resets for each client IP.
Longer: clients stay rate-limited for longer after hitting the cap — harder to recover.
Shorter: window resets sooner — rate limit clears faster after being triggered.
Max per Window
RATE_LIMIT_MAX
Default: 10000
requests per window
 Maximum requests a single client IP can make in one window before receiving 429. The default 10000 is effectively unlimited for local testing.
Lower (e.g. 30–100): triggers 429 quickly — good for observing error handling in JMeter reports.
Higher: nearly impossible to hit — rate limiting is on but does not interfere.

Concurrency

A hard cap on how many requests can be in-flight at the same time. When the cap is reached, any new incoming request immediately receives 503 Service Unavailable. This simulates a server that is genuinely too busy to queue more work.
Setting Value What it controls
Max Concurrent Requests
MAX_CONCURRENT
Default: 50
simultaneous requests
 Maximum number of requests being processed at the same time. Any request arriving while the cap is full gets 503 instantly. The count drops as responses finish, so the limit is self-correcting.
Lower (e.g. 5–10): produces 503s quickly when JMeter threads exceed the cap — good for testing error handling and retry logic.
Higher: harder to saturate — useful for load-testing endpoints without introducing 503 noise.
Setting this below 3 may make this Config page unreachable while a load test is running. The /api/config endpoint is always accessible and can be used to recover via curl.

Workload Endpoints

These control the simulation behavior of /slow, /busy, /cpu, /memory, and /io. Changes apply to the next request — no restart needed.
Setting Value What it controls
/slow — Delay
SLOW_DELAY_MS
Default: 200 ms
milliseconds
 How long GET /slow waits before responding. Simulates a sluggish database call or I/O-bound operation. The delay is async (non-blocking) so other concurrent requests are not affected.
Higher (e.g. 1000–2000 ms): directly raises p95/p99 — easy to observe in JMeter's Aggregate Report.
0 ms: /slow behaves like /fast — useful to isolate other bottlenecks.
/busy — Delay
BUSY_DELAY_MS
Default: 3000 ms
milliseconds
 How long GET /busy waits before responding. Simulates a heavy background job (report generation, external API call). Long delays cause requests to pile up — combine with a low Max Concurrent to produce sustained 503 pressure.
Higher (e.g. 8000–15000 ms): active requests fill the concurrency cap quickly, yielding 503s even with a few JMeter threads.
0 ms: removes the bottleneck — useful when testing other parts of a flow.
/cpu — Iterations
CPU_ITERATIONS
Default: 10,000,000
loop iterations
 Number of iterations in the synchronous CPU loop run by GET /cpu. This blocks Node.js's event loop while running — all other in-flight requests stall until it completes. At 10M iterations expect roughly 20–50 ms on modern hardware.
Higher (e.g. 50M–100M): blocks the event loop for 100–500 ms — latency of all endpoints rises under concurrent /cpu load.
1000: effectively instant — removes the CPU bottleneck without changing the route.
/memory — Array Size
MEMORY_ARRAY_SIZE
Default: 1,000,000
array elements
 Number of elements allocated and filled during each GET /memory request. The array is discarded after the response, creating garbage collection pressure under load. At the default 1M elements of "test", each request allocates roughly 4–8 MB.
Higher (e.g. 5M–10M): 20–80 MB per request — GC pauses become visible and latency drifts upward under concurrent load.
1000: trivial allocation — removes memory pressure for isolation testing.
/io — File Size
IO_FILE_SIZE_KB
Default: 1024 KB
kilobytes
 Size of the file written or read by GET /io (stored at tmp/io-test.dat). I/O is async so it does not block the event loop, but disk throughput saturation adds latency under concurrent load.
Higher (e.g. 10 MB–50 MB): I/O duration increases — disk saturation visible in JMeter when many threads hit /io simultaneously.
10 KB: near-instant — removes I/O latency without disabling the route.
