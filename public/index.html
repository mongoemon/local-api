Performance Testing Lab

Performance Testing Lab คือ local API สำหรับเรียนรู้ load testing และ performance monitoring บนเครื่องตัวเองอย่างปลอดภัย

ยังใหม่อยู่? เริ่มจากหน้านี้แล้วทำทีละขั้นตามลำดับ ไม่ต้องรีบ ทำทีละอย่างจะเข้าใจได้เร็วกว่า

🗺️ Learning Path (เริ่มจากนี้)

Step 1 — เข้าใจ API นี้ทำอะไร (5 นาที)

อ่านตาราง Endpoint Purpose ด้านล่างเพื่อรู้ว่าแต่ละ endpoint ออกแบบมาทดสอบอะไร เช่น /fast ใช้วัด baseline latency, /busy ใช้ชน concurrency limit, /demo/* ใช้จำลอง e-commerce

Step 2 — ลองเรียก endpoint ผ่าน browser (5–10 นาที)

คลิกลิงค์ใน Try These Endpoints ด้านล่างเพื่อดู response จริงจากแต่ละ endpoint ก่อนเริ่มทำ JMeter

Step 3 — เรียน demo transaction flow

เปิด Demo Learning Path แล้วลองเรียก e-commerce flow ตั้งแต่ context → search → add to cart → checkout → order status

Step 4 — สร้าง JMeter test plan

เปิด JMeter Guide แล้วทำตามลำดับ: ตั้ง HTTP Request Defaults → สร้าง Thread Group → เพิ่ม Transaction Controller → ใส่ JSON Extractor

Step 5 — เลือก test type และ thread group

เปิด Test Types เพื่อเลือกว่าจะทดสอบแบบ load, stress, spike, หรือ endurance และควรใช้ thread group แบบไหน

Step 6 — ฝึกด้วยโจทย์จริง

เปิด Assignment แล้วทำโจทย์ตั้งแต่ task พื้นฐานไปถึง performance testing จริง

🔗 Try These Endpoints (Step 2)

คลิกลิงค์เพื่อเรียก endpoint และดู response จริง — GET endpoints คลิกได้ทันที, POST ต้องใช้ Postman หรือ curl

  • /fast — baseline, ตอบทันที
  • /slow — หน่วง 200ms
  • /busy — หน่วง 3000ms, ใช้ชน concurrency limit
  • /cpu — CPU workload
  • /memory — memory allocation
  • /io?mode=read — อ่านไฟล์จาก disk
  • /io?mode=write — เขียนไฟล์ไป disk
  • /prep — สร้าง token seed สำหรับ /protected
  • GET /protected — ต้องส่ง token, ลองผ่าน Postman
  • /error — จำลอง 500 error
  • /status — runtime info
  • /metrics — Prometheus metrics
  • POST /auth/login — รับ JWT token (ใช้ Postman)
  • POST /auth/verify — ตรวจสอบ JWT token
  • POST /submit-one — ทดสอบ body validation (1 field)
  • POST /submit-two — ทดสอบ body validation (2 fields)
  • POST /cleanup — ล้างไฟล์ชั่วคราวจาก /io

Demo endpoints: /demo/context · /demo/dashboard · /demo/search?q=mouse · /demo/product/details?productId=sku-101

Gold standard ในหน้านี้หมายถึง baseline เป้าหมายสำหรับ API ใน lab นี้ ไม่ใช่ SLA กลางสำหรับทุก production system ปรับตาม business criticality และ infrastructure จริง

📘 Endpoint Purpose And SLA (Step 3)

Endpoint ใช้ทดสอบอะไร Gold Standard / SLA แนะนำ
/fast baseline endpoint — วัด latency ต่ำสุดของระบบเมื่อแทบไม่มีงานฝั่ง server p95 < 100 ms, error rate < 1%
/slow จำลอง downstream latency คงที่ — ดู timeout, queueing behavior, latency budget p95 < 300 ms (รวม delay ที่ตั้ง), error < 1%
/busy บังคับ in-flight requests สูงจนชน concurrency limit เพื่อดู 503 backpressure ไม่มี user-facing SLA — ใช้ยืนยันว่า backpressure ทำงานจริง
/cpu CPU saturation และ event-loop blocking p95 ไม่พุ่งจนกระทบ endpoint อื่น, 5xx < 2%
/memory memory pressure, GC pause, โอกาสเกิด OOM process ไม่โตต่อเนื่อง, error rate < 1%
/prep สร้าง seed สำหรับ JMeter pre-processor — requestId, token, authorizationHeader ตอบเร็ว สม่ำเสมอ ไม่มีภาระหนัก
/protected ทดสอบ auth header flow — รับ Authorization: Bearer ... และ x-access-token 200 token ถูก, 401 ไม่มี token, 403 token ผิด
/io?mode=read|write I/O bottleneck จากการอ่าน/เขียนไฟล์จริงใน tmp/ ดู durationMs ที่ response — ใช้ดู disk throughput
POST /cleanup ล้างไฟล์ชั่วคราวหลัง /io — ใช้ใน tearDown Thread Group ตอบ 200 เสมอ แม้ไม่มีไฟล์ให้ลบ
POST /submit-one validation ของ request body — required 1 field: name 200 ส่งครบ, 400 ส่งไม่ครบ
POST /submit-two validation ของ request body — required 2 fields: name และ type 200 ส่งครบ, 400 ขาด field
/error จำลอง HTTP 500 แบบตั้งใจ — ใช้ทดสอบ error handling, retry, alerting ไม่ใช่ gold endpoint — ควรได้ 500 ทุก request
/status runtime health check — pid, startedAt, uptimeSec, activeRequests ตอบ 200 ตลอดเมื่อ process ยังทำงาน
/metrics Prometheus scrape endpoint — throughput, latency, request counts เสถียร ไม่ทำให้ request อื่นช้า
POST /auth/login JWT authentication — ส่ง username/password รับ JWT token อายุ 24 ชั่วโมง 200 credentials ถูก, 401 ผิด, error < 1%
POST /auth/verify ตรวจสอบ JWT token — ส่ง Authorization: Bearer <token> 200 token valid, 401 หมดอายุ, 403 invalid

🔥 How To Trigger Each Scenario

เป้าหมายEndpointค่าที่แนะนำคาดว่าจะเจอ
วัด baseline latency /fast 10–50 users, ramp-up 1–5 sec 200 เกือบทั้งหมด, latency ต่ำ
ดูผล latency คงที่ /slow 50–100 users, SLOW_DELAY_MS=200–1000 200 แต่ response time สูงตาม delay
ชน concurrency limit /busy 100–300 users, MAX_CONCURRENT=20–50, BUSY_DELAY_MS=3000 บาง request ได้ 200, บางได้ 503
ดู CPU bottleneck /cpu 20–100 users, CPU_ITERATIONS=10M–100M 200 แต่ latency สูง, endpoint อื่นช้าตาม
ดู memory pressure /memory 20–100 users, MEMORY_ARRAY_SIZE=1M–5M response time แกว่ง, memory usage สูง
ทดสอบ auth header /protected 1–50 users, header Authorization: Bearer lab-token token ถูก 200, ไม่มี 401, ผิด 403
ดู I/O bottleneck /io?mode=read|write 20–100 users, IO_FILE_SIZE_KB=1024–8192 durationMs สูงตามขนาดไฟล์
ทดสอบ body validation POST /submit-one, /submit-two ส่ง JSON body ถูก/ผิด ส่งครบ 200, ขาด field 400
ทดสอบ 5xx path /error 1–50 users 500 ทุก request
ล้าง temp data POST /cleanup 1 user ใน tearDown Thread Group 200 พร้อม cleaned list

💬 Response Meanings

  • /fast → { "message": "fast response" } — endpoint ไม่มี workload ตอบสำเร็จ
  • /slow → slow response (Xms) — server หน่วงตาม SLOW_DELAY_MS
  • /busy → busy response (Xms) ถ้าผ่านได้; 503 Server too busy (plain text) ถ้าชน limit
  • /cpu → result คือผลรวม loop, iterations คือจำนวนรอบ
  • /memory → size คือจำนวน element ที่ allocate สำเร็จ
  • /prep → มี token, authorizationHeader, requestId, timestamp
  • /protected → authenticated: true ถ้า token ถูก; missing_token หรือ invalid_token ถ้าผิด
  • /io → mode, fileSizeKb, durationMs
  • POST /cleanup → cleaned รายการที่ลบได้, cleanedCount
  • POST /submit-one → received one required parameter หรือ missing_required_parameter
  • POST /submit-two → received two required parameters หรือ missing_required_parameters
  • /error → intentional server error — ตั้งใจตอบ 500
  • /status → running: true, pid, startedAt, uptimeSec, activeRequests
  • /metrics → Prometheus text format ไม่ใช่ JSON
  • POST /auth/login → token (JWT string) เมื่อ credentials ถูก
  • POST /auth/verify → valid: true, decoded เมื่อ token ถูก; token_expired หรือ invalid_token

📏 SLA Interpretation

  • ดู p95 หรือ p99 มากกว่าค่าเฉลี่ย — percentile สะท้อนประสบการณ์ผู้ใช้จริงเมื่อระบบเริ่มแน่น
  • Error rate — ถ้า 5xx หรือ timeout เกิน 1% ใน endpoint หลัก ถือว่าระบบเริ่มไม่ผ่านเกณฑ์
  • Availability — สำหรับ /status ควรตั้งเป้า 99.9% ขึ้นไป
  • Isolation — ถ้าโหลด /cpu แล้วทำให้ /fast หลุด SLA แปลว่า workload แยก resource ไม่ดีพอ
