📘 Endpoint Purpose And SLA (Step 3)

Endpoint ใช้ทดสอบอะไร Gold Standard / SLA ที่แนะนำ
/fast ใช้เป็น baseline endpoint สำหรับวัด latency ต่ำสุดของระบบเมื่อแทบไม่มีงานหนักฝั่ง server เหมาะใช้เป็น reference SLA: p95 < 100 ms, error rate < 1%, success rate >= 99%
/slow ใช้จำลอง downstream latency หรือ service ที่ตอบช้าคงที่ เพื่อดูว่า client, timeout และ queueing behavior รับมือได้แค่ไหน SLA ควรยอมรับ delay ตาม design ได้สม่ำเสมอ เช่น p95 < 300 ms, error rate < 1%; ถ้าเกินจาก 200 ms ที่ตั้งใจไว้มาก แปลว่ามี overhead เพิ่มจากระบบ
/busy ใช้ทำให้ request ค้างนานโดยตั้งใจ เพื่อให้จำนวน in-flight requests สูงพอที่จะชน concurrency limit และได้ 503 Server too busy ไม่ได้มี SLA แบบ user-facing ปกติ แต่ใช้ยืนยันว่า backpressure ทำงานจริงเมื่อโหลดเกินขีดจำกัด
/cpu ใช้ทดสอบ CPU saturation, event-loop blocking และผลกระทบเมื่อมี request ใช้ compute สูง ไม่ควรใช้เป็น gold endpoint ฝั่ง user-facing โดยตรง แต่ใช้ดู capacity ceiling; SLA ที่ควรดูคือ p95 ไม่พุ่งจนกระทบ endpoint อื่น และ 5xx ไม่ควรเกิน 1-2%
/memory ใช้จำลอง allocation หนัก เพื่อดู memory pressure, GC pause และโอกาสเกิด OOM เมื่อมี concurrent requests เกณฑ์สำคัญคือ process ต้องไม่โตต่อเนื่อง, ไม่ crash, และ error rate ควรต่ำกว่า 1%; ถ้า response time แกว่งมากแปลว่า GC เริ่มมีผลต่อ SLA
/prep ใช้เป็น endpoint เรียบง่ายสำหรับสร้างค่า seed เช่น requestId, token, authorizationHeader, timestamp เพื่อเอาไปใช้ต่อใน JMeter pre-processor หรือ JSON extractor ควรตอบเร็วและสม่ำเสมอ; เหมาะสำหรับ setup step ก่อนยิง request หลัก ไม่ได้มีภาระหนัก
/protected ใช้ทดสอบ endpoint ที่ต้องมี token โดยรับทั้ง header แบบ Authorization: Bearer ... และ x-access-token เหมาะสำหรับทดสอบ auth flow, header injection และ negative cases เช่น 401/403; default token คือ lab-token
/io?mode=read|write ใช้จำลอง I/O bottleneck จริงด้วยการอ่านหรือเขียนไฟล์ลง disk ในโฟลเดอร์ tmp ใช้ดู read/write latency, throughput และผลกระทบของ storage; เหมาะสำหรับเทส disk-bound workload มากกว่า user-facing SLA ปกติ
POST /cleanup ใช้ล้างข้อมูลชั่วคราวที่เกิดจากการทดสอบ เช่นไฟล์จาก /io เพื่อให้รอบถัดไปเริ่มจาก state ที่สะอาด เหมาะสำหรับ teardown flow มากกว่า SLA ปกติ; ควรตอบ 200 แม้ไม่มีไฟล์ให้ลบ และคืนรายการสิ่งที่ล้างสำเร็จ
POST /submit-one ใช้ทดสอบ validation ของ request body กรณีที่ API ต้องรับ parameter บังคับ 1 ตัวคือ name ควรตอบ 200 เมื่อส่งค่าครบ และตอบ 400 เมื่อไม่ส่ง name; เหมาะสำหรับทดสอบ client-side request building
POST /submit-two ใช้ทดสอบ validation ของ request body กรณีที่ API ต้องรับ parameter บังคับ 2 ตัวคือ name และ type ควรตอบ 200 เมื่อส่งค่าครบ และตอบ 400 เมื่อขาด field ใด field หนึ่ง; เหมาะสำหรับ JMeter/Postman form testing
/error ใช้จำลอง server error แบบตั้งใจเพื่อให้เกิด HTTP 500 ใช้วัด error rate, retry behavior และ alerting; ไม่ใช่ gold endpoint สำหรับ SLA ปกติ
/status ใช้เช็กอย่างรวดเร็วว่า instance นี้ยังรันอยู่หรือไม่ พร้อมดู pid, startedAt, uptime และ activeRequests ควรตอบ 200 เสมอเมื่อ process ยังทำงาน; เหมาะสำหรับเช็กแบบ manual เวลาไม่แน่ใจว่า index.js ยังเปิดอยู่หรือไม่
/metrics ใช้ให้ Prometheus หรือ monitoring agent มา scrape metric สำหรับดู throughput, latency และสถานะระบบ ไม่จำเป็นต้องเร็วเท่า user endpoint แต่ต้องเสถียร; scrape ควรสำเร็จเกือบทั้งหมด และไม่ควรทำให้ request ปกติช้าลง
POST /auth/login ใช้สำหรับ JWT authentication - ส่ง username/password เพื่อรับ JWT token ที่ใช้ได้ 24 ชั่วโมง ควรตอบ 200 เมื่อ credentials ถูก (username=demo, password=password) พร้อม token, ตอบ 401 เมื่อ credentials ผิด, error rate < 1%
POST /auth/verify ใช้สำหรับตรวจสอบความถูกต้องของ JWT token - ส่ง token ในHeader Authorization: Bearer <token> เพื่ออ่านข้อมูลผู้ใช้ที่อยู่ใน token ควรตอบ 200 ถ้า token ถูกต้องและยังไม่หมดอายุ, ตอบ 401 ถ้า token หมดอายุ, ตอบ 403 ถ้า token ไม่ถูกต้อง, error rate < 1%

🔥 How to Trigger Scenarios (Step 4)

  • /fast → ใช้ตั้ง baseline SLA ของระบบ
  • /slow → ใช้ทดสอบ timeout, retry และ latency budget
  • /busy → ใช้บังคับให้ชน concurrency limit และเห็น 503 ชัดเจน
  • /cpu → ใช้หา CPU bottleneck และดูผลต่อ concurrent traffic
  • /memory → ใช้จับ memory pressure และอาการก่อน crash
  • /prep → ใช้สร้างค่า requestId/token/authorizationHeader แบบง่ายเพื่อส่งต่อให้ request ถัดไป
  • /protected → ใช้ทดสอบ request ที่ต้องแนบ token และดู 401/403/200 ตามกรณี
  • /io → ใช้จับ I/O bottleneck จากการอ่านหรือเขียนไฟล์จริง
  • POST /cleanup → ใช้ล้างข้อมูลชั่วคราวหลังจบรอบเทส
  • POST /submit-one → ใช้ทดสอบ body validation แบบ required 1 field
  • POST /submit-two → ใช้ทดสอบ body validation แบบ required 2 fields
  • /error → ใช้ทดสอบ 5xx, alerting และ retry behavior
  • /status → ใช้เช็กตรง ๆ ว่า process ยังรันอยู่ พร้อมดู uptime และ pid
  • /metrics → ใช้ scrape metrics เพื่อเทียบผลกับ SLA และ capacity trend
  • POST /auth/login → ใช้ login เพื่อรับ JWT token
  • POST /auth/verify → ใช้ตรวจสอบว่า JWT token ยังใช้ได้

📏 SLA Interpretation

  • Latency SLA: ดู p95 หรือ p99 มากกว่าค่าเฉลี่ย เพราะสะท้อนประสบการณ์ของผู้ใช้จริงตอนระบบเริ่มแน่น
  • Error SLA: ถ้า 5xx หรือ timeout เกิน 1% ใน endpoint หลัก ถือว่าระบบเริ่มไม่ผ่านเกณฑ์สำหรับงานทั่วไป
  • Availability SLA: สำหรับ endpoint สำคัญเช่น /status ควรตั้งเป้า 99.9% ขึ้นไป
  • Isolation: ถ้าโหลด /cpu หรือ /memory แล้วทำให้ /fast หลุด SLA แปลว่า workload ยังแยก resource ไม่ดีพอ

🧭 Test Guideline

เป้าหมาย Endpoint ค่าที่แนะนำ คาดว่าจะเจอ
วัด baseline latency /fast 10-50 users, ramp-up 1-5 sec ส่วนใหญ่ได้ 200, latency ต่ำ, error rate ใกล้ 0
ดูผลของ latency คงที่ /slow 50-100 users, SLOW_DELAY_MS=200-1000 ได้ 200 แต่ response time สูงขึ้นตาม delay ที่ตั้ง
ชน concurrency limit /busy 100-300 users, ramp-up 0-1 sec, MAX_CONCURRENT=20-50, BUSY_DELAY_MS=3000 บาง request ได้ 200, บาง request ได้ 503 Server too busy
ดู CPU bottleneck /cpu 20-100 users, CPU_ITERATIONS=10000000-100000000 ยังได้ 200 แต่ latency สูง และ endpoint อื่นอาจช้าตาม
ดู memory pressure /memory 20-100 users, MEMORY_ARRAY_SIZE=1000000-5000000 response time แกว่ง, memory usage สูง, ถ้าหนักมากอาจ crash
สร้าง pre-processor seed /prep 1-20 users, no special config ได้ requestId, token, authorizationHeader เพื่อนำไปใช้เรียก /protected ต่อได้ทันที
ทดสอบ token auth /protected 1-50 users, ตั้ง header Authorization: Bearer lab-token หรือกำหนด AUTH_BEARER_TOKEN ส่ง token ถูกได้ 200, ไม่ส่งได้ 401, ส่งผิดได้ 403
ดู I/O bottleneck /io?mode=read หรือ /io?mode=write 20-100 users, IO_FILE_SIZE_KB=1024-8192 duration สูงขึ้นตามขนาดไฟล์และชนิดของ I/O ที่ใช้
ล้าง temp data หลังเทส POST /cleanup 1 user, loop 1, ใช้ใน tearDown Thread Group ได้ 200 และคืนรายการไฟล์ที่ถูกล้างใน cleaned
ทดสอบ validation 1 field POST /submit-one ส่ง JSON { "name": "demo" } ส่งครบได้ 200, ส่งไม่ครบได้ 400
ทดสอบ validation 2 fields POST /submit-two ส่ง JSON { "name": "demo", "type": "load-test" } ส่งครบได้ 200, ขาด field ได้ 400
ทดสอบ 5xx /error 1-50 users, ramp-up 0-2 sec ได้ 500 ทุก request

💬 Response Meaning

  • /fast → { "message": "fast response" } หมายถึง endpoint baseline ตอบสำเร็จแบบไม่มี workload พิเศษ
  • /slow → slow response (Xms) หมายถึง server หน่วงเวลาตาม SLOW_DELAY_MS ก่อนตอบ
  • /busy → busy response (Xms) หมายถึง request ผ่านเข้าไปประมวลผลได้; ถ้าไม่ผ่านจะได้ 503 Server too busy
  • /cpu → result คือผลรวมจาก loop, iterations คือจำนวนรอบที่ใช้สร้าง CPU load
  • /memory → size คือจำนวน element ที่ server allocate สำเร็จใน request นั้น
  • /prep → token และ authorizationHeader เป็น static credential สำหรับส่งต่อไป /protected, ส่วน requestId และ timestamp ใช้เป็น dynamic test data
  • /protected → ถ้าไม่มี token จะได้ missing_token, ถ้า token ผิดจะได้ invalid_token, ถ้าถูกจะได้ authenticated: true
  • /io → mode บอกว่า read หรือ write, fileSizeKb คือขนาดไฟล์, durationMs คือเวลาที่ใช้กับ I/O operation
  • POST /cleanup → cleaned คือรายการ resource ที่ลบได้จริง และ cleanedCount คือจำนวนที่ถูกล้าง
  • POST /submit-one → received one required parameter แปลว่าส่ง name มาครบ; ถ้าไม่ครบจะได้ missing_required_parameter
  • POST /submit-two → received two required parameters แปลว่าส่ง name และ type ครบ; ถ้าขาดจะได้ missing_required_parameters
  • /error → intentional server error แปลว่า server ตั้งใจตอบ 500 เพื่อใช้ทดสอบ error path
  • /status → ถ้าได้ running: true แปลว่า instance นี้ยังทำงานอยู่ และจะบอก pid, startedAt, uptimeSec, activeRequests
  • /metrics → เป็น Prometheus text format สำหรับ monitoring ไม่ใช่ JSON สำหรับผู้ใช้ทั่วไป
  • POST /auth/login → { "token": "jwt-token" } แปลว่า login สำเร็จ ได้ JWT token
  • POST /auth/verify → ถ้าได้ valid: true แปลว่า token ยังใช้ได้ ถ้าได้ token_expired หรือ invalid_token แปลว่า token ติดปัญหา

🧵 JMeter Thread Group Mapping (Step 5b - Choose Thread Group Type)

Normal Thread Group

  • เหมาะกับ Baseline, Baseline Health, Latency Test, Validation, Failure Path, Soak
  • ใช้กับ /fast, /slow, /status, /error, POST /submit-one, POST /submit-two
  • เพิ่ม /protected เมื่ออยากเทส auth header แบบเบา ๆ
  • เหมาะเมื่ออยากได้ fixed load แบบตรงไปตรงมาเพื่อดู SLA, latency และ error rate
  • ค่าที่แนะนำ: Threads 20-50, Ramp-Up 1-5 sec, Loop Count 20-100; ถ้าเป็น soak test ใช้ Duration 15-60 min

Concurrency Thread Group

  • เหมาะกับ Stress, CPU Stress, Memory Stress, IO Stress
  • ใช้กับ /busy, /cpu, /memory, /io
  • เหมาะเมื่ออยากคุมจำนวน active users จริงเพื่อให้เห็น runtime limit, 503, blocking และ saturation
  • ค่าที่แนะนำ: Target Concurrency 50-300, Ramp-Up Time 30-60 sec, Ramp-Up Steps Count 5-10, Hold Target Rate Time 30-180 sec

Stepping Thread Group

  • เหมาะกับ Spike, Rate Limit และ stress test แบบไต่ระดับ
  • ใช้กับ /busy และ /fast
  • เหมาะเมื่ออยากเห็นว่าที่ step ไหนระบบเริ่มได้ 429 หรือ 503
  • ค่าที่แนะนำ: Start Users Count 0, Initial Delay 0 sec, Start Users Count per Step 20-50, Start Users Period 5-15 sec, Stop Users Count 20-50, Flight Time 30-120 sec

📌 Thread Group Recommendation By Scenario (Step 5c - Pick Your Scenario)

Scenario Layer Thread Group ค่าที่แนะนำ เหตุผล
Baseline Application Normal Threads 20, Ramp-Up 2 sec, Loop 100 ใช้ fixed load เพื่อวัด SLA baseline
Latency Test Application Normal Threads 50, Ramp-Up 2 sec, Loop 50 ดูผลของ delay คงที่ได้ตรงที่สุด
Validation Application Normal Threads 20, Ramp-Up 1 sec, Loop 20 ใช้ดู 200/400 จาก request body
Token Auth Application Normal Threads 20, Ramp-Up 1 sec, Loop 20 ใช้ดู 200/401/403 จาก auth header
Failure Path Application Normal Threads 20, Ramp-Up 1 sec, Loop 20 ใช้วัด 500 rate แบบตรงไปตรงมา
Soak Application Normal Threads 30-50, Ramp-Up 10 sec, Duration 15-60 min เหมาะกับโหลดคงที่ระยะยาว
Stress Runtime Concurrency Target 150, Ramp-Up 60 sec, Steps 10, Hold 60 sec ต้องรักษา active users ให้สูงพอ
Spike Runtime Stepping Step 50 users every 5 sec, Flight Time 30 sec ใช้หา threshold ว่าระบบเริ่ม reject ตอน step ไหน
CPU Stress Runtime Concurrency Target 50, Ramp-Up 30 sec, Steps 5, Hold 60 sec ต้อง sustain load เพื่อให้เห็น blocking และ CPU saturation
Memory Stress Runtime Concurrency Target 30, Ramp-Up 30 sec, Steps 5, Hold 60 sec ต้อง sustain load เพื่อให้เห็น memory pressure
Rate Limit Runtime Stepping Step 20-30 users every 5-10 sec, Flight Time 60 sec ใช้ไล่ step เพื่อดูจุดที่เริ่มได้ 429
CPU Bottleneck Infrastructure Concurrency Target 50, Ramp-Up 30 sec, Steps 5, Hold 60 sec ต้องคุม concurrency คู่กับ CPU limit
Memory Bottleneck Infrastructure Concurrency Target 30, Ramp-Up 30 sec, Steps 5, Hold 60 sec ต้องคุม concurrency คู่กับ memory limit
IO Stress Infrastructure Concurrency Target 30, Ramp-Up 30 sec, Steps 5, Hold 60 sec ต้อง sustain concurrent read/write ให้เห็น I/O bottleneck

🧱 Metrics Layers

Layer เป้าหมาย Endpoint ที่เกี่ยวข้อง
Application Metrics validate SLA/SLO และวัดจากมุม end-user /fast, /slow, /status, /error, POST /submit-one, POST /submit-two
Runtime Metrics หา concurrency limit, runtime ceiling และ processing bottleneck /busy, /cpu, /memory, /metrics
Infrastructure Metrics หา CPU, memory และ disk I/O bottleneck ของ host/container /cpu, /memory, /io?mode=read, /io?mode=write
Database Metrics หา slow query, locking และ connection constraints ยังไม่มี endpoint จริงในโปรเจกต์นี้
