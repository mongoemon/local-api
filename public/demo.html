4. Read The Result

หลังจากรัน test เสร็จ อย่าดูแค่ request ผ่านหรือไม่ผ่าน ให้ดู 4 อย่างพร้อมกัน: transaction time, error rate, throughput, และ traffic mix ว่าตรงกับความต้องการลูกค้าหรือไม่

What To Open In JMeter

ComponentUse It To CheckWhy It Matters
View Results Treeresponse จริงของแต่ละ requestใช้ debug เมื่อ request fail, variable ไม่ถูก extract, หรือ body/header ผิด
Summary Reportaverage, min, max, error %, throughputใช้ดูภาพรวมเร็ว ๆ ว่ารอบ test ผ่าน SLA ขั้นต้นหรือไม่
Aggregate Reportmedian, 90%, 95%, 99%ใช้ตัดสิน SLA เพราะ percentile สำคัญกว่าค่าเฉลี่ย
Transaction Controller Parent Sampleเวลารวมของ flowใช้ตอบลูกค้าว่า user journey ทั้งก้อนเร็วพอหรือไม่ ไม่ใช่ดูแค่ step เดี่ยว
Backend Listener ถ้ามีmetric ต่อเนื่องระหว่างรันนาน ๆใช้ดู drift ใน load/endurance test

What To Look At First

  1. ดู Error % ก่อน ถ้ายังมี error สูง แปลว่ายังไม่ผ่านก่อนดู latency
  2. ดู 90%, 95%, 99% ใน Aggregate Report
  3. ดู parent sample ของ Transaction Controller ว่า flow รวมใช้เวลาเท่าไร
  4. ดู Throughput Controller ว่า sample count ของ cart flow ใกล้กับ % ที่ตั้งไว้หรือไม่
  5. ถ้ามี If Controller ให้เช็กว่า order status ถูกเรียกเฉพาะตอนมี orderId จริง

Example Interpretation

Customer requirement
- Browse flow p95 < 800 ms
- Add And Checkout p95 < 1500 ms
- Error rate < 1%
- Cart flow around 40% of total browse traffic

Test result
- Browse Flow p95 = 620 ms
- Add And Checkout p95 = 1320 ms
- Error rate = 0.3%
- Browse sample count = 1000
- Cart flow sample count = 392

Interpretation
- Browse flow passed
- Add And Checkout passed
- Error rate passed
- Cart flow mix passed because 392/1000 = 39.2%
- Overall result: this test run matches the customer target

Example Of A Failed Result

Customer requirement
- Add And Checkout p95 < 1500 ms
- Error rate < 1%

Test result
- Add And Checkout p95 = 2400 ms
- Error rate = 3.8%

Interpretation
- Transaction is too slow at the tested load
- Reliability is below target
- This run does not meet the customer SLA
- Next action: reduce load, inspect failed samplers, or tune app/runtime before rerun

How To Tell The Result Matches Customer Needs

  • ต้องเขียน pass criteria ก่อนรันเสมอ เช่น p95, error %, throughput, และ traffic mix
  • อย่าใช้แค่ค่า Average เพราะลูกค้ามักสนใจประสบการณ์ส่วนใหญ่ของผู้ใช้ ซึ่งดูจาก percentile
  • ถ้าลูกค้าพูดถึง flow เช่น browse, checkout, order lookup ให้ดู parent sample ของ transaction เป็นหลัก
  • ถ้าลูกค้าพูดถึงสัดส่วน traffic เช่น มีเพียงบางคน checkout ให้ดู sample count ของ flow ใต้ Throughput Controller
  • ถ้าผลยังไม่ตรง SLA ให้บอกชัดว่า fail ที่ค่าไหนและที่โหลดระดับไหน เช่น p95 breach at 50 users

SLA By Test Type

SLA ไม่ควรถูกดูแบบเหมารวมทุก test type ต้องดูว่า SLA นั้นตั้งใจใช้กับโหลดปกติ, ช่วงพีค, การกดดันจนเกิน capacity, หรือความเสถียรระยะยาว
Test TypeShould You Use It For SLA?What It Usually Proves
Load Testใช่ เป็นตัวหลักระบบยังผ่าน SLA ภายใต้ expected traffic จริงหรือไม่
Stress Testใช้ได้ แต่เป็น threshold SLAระบบเริ่ม degrade หรือ fail ที่โหลดระดับไหน
Spike Testใช้ได้ ถ้า SLA พูดถึง peak หรือ recoveryระบบรับโหลดพุ่งเร็วได้ไหม และ recover กลับมาในกี่วินาที
Endurance Testใช้ได้ ถ้า SLA พูดถึง stabilitySLA ยังนิ่งหรือ drift เมื่อรันนาน ๆ

If The SLA SaysUse This Test Type FirstWhy
รองรับผู้ใช้หรือ request ในภาวะปกติLoad Testเป็นการพิสูจน์ target หลักใน expected traffic
ห้ามพังแม้โหลดสูงกว่าปกติStress Testใช้หา degradation point และ failure threshold

ต้องนิ่งตลอดวันหรือหลายชั่วโมงEndurance Testใช้จับ latency drift, leak, และ stability ปลายรอบ

How To Analyze These SLA Statements

Statement
"At expected business load, the full checkout journey must complete within 1.5 s for 95% of users."

Analysis
- This is a user journey statement, not a single endpoint statement
- Main metric is transaction p95
- Main test type is Load Test
- Best component is Transaction Controller parent sample
- Pass only if tested at expected load, not at 1 user only
Statement
"The service must remain available until at least 80 concurrent users; after that point graceful degradation is acceptable."

Analysis
- This is a capacity threshold statement
- Main test type is Stress Test
- Best thread group is Concurrency Thread Group
- Pass if the system still meets availability/error target below 80 concurrent users
- After 80, slower response or some rejection may be acceptable depending on the statement
Statement
"During campaign launch, traffic may jump to 3x normal within one minute, and the API must recover within 2 minutes."

Analysis
- This is not a normal SLA-only statement
- Main test type is Spike Test
- Focus on error burst, percentile jump, and recovery window
- Pass only if the system returns to acceptable latency/error within the stated recovery time

POC SLA Statement

Customer SLA Statement
"Under normal business load, the demo browse flow must complete with p95 below 800 ms,
and the Add And Checkout transaction must complete with p95 below 1500 ms,
with error rate below 1%.
Around 40% of browse sessions are expected to continue to cart and checkout."

POC Test Type Decision

Recommended test type: Load Test

Reason
- The statement talks about normal business load
- It includes a browse flow target
- It includes a checkout transaction target
- It includes a traffic mix target of 40%
