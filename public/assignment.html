Assignment for Beginners

หน้านี้เป็นชุดโจทย์สำหรับผู้เริ่มต้น เพื่อให้ลองใช้งาน API ทีละส่วนและเห็นคำตอบทันที เหมาะสำหรับฝึกเขียน request, อ่าน response, และเข้าใจวัตถุประสงค์ของแต่ละ endpoint

How to use

  • อ่านโจทย์ในแต่ละส่วนก่อน
  • ลองเรียก endpoint ด้วย browser, Postman, หรือ curl
  • อ่านเฉลยด้านล่างแต่ละ task เพื่อยืนยันคำตอบ
ก่อนเริ่ม ให้ศึกษา JMeter Guide สำหรับการตั้งค่า Thread Group, Variables, และ Extractors และ Test Types สำหรับการเลือกประเภทการทดสอบและ run order

Task 1: เรียกแบสลายน์ endpoint

โจทย์

เรียก GET /fast แล้วตรวจสอบว่า response มีข้อความว่าอะไร

วิธีทำ
  • ใช้ browser, curl หรือ Postman เปิด URL http://localhost:3001/fast
  • สำหรับ test baseline ให้เริ่มด้วย 1 thread หรือ 1 request เดียว
  • ดู response ว่าเป็น JSON และมี field message
  • ตรวจสอบว่า message คือ fast response
เฉลย

Response ที่ถูกต้องจะเป็น JSON:

{
  "message": "fast response"
}

ถ้าได้ response นี้ แปลว่า server ทำงานและ endpoint baseline ตอบได้ตามปกติ

Task 2: ทดสอบ delay endpoint

โจทย์

เรียก GET /slow แล้วสังเกตเวลาที่ใช้กับ request และข้อความใน response

วิธีทำ
  • ใช้ curl หรือ Postman เรียก http://localhost:3001/slow
  • เริ่มด้วย 1-2 threads หรือ 1-2 concurrent requests เพื่อดู delay ที่ชัดเจน
  • จดเวลาตั้งแต่ส่ง request จนได้ response
  • ดูว่า response message ระบุ delay เช่น slow response (200ms)
เฉลย

Response ที่ได้จะเป็น JSON ประมาณนี้:

{
  "message": "slow response (200ms)"
}

ค่าตัวเลขหลัง slow response จะมาจากการตั้งค่า config.workloads.slowDelayMs ในระบบ

Task 3: ตรวจสอบ auth flow แบบเก่า

โจทย์

เรียก GET /prep เพื่อดู token และ authorization header ที่ระบบให้ จากนั้นลองเรียก GET /protected โดยส่ง header Authorization: Bearer lab-token

วิธีทำ
  • เปิด GET http://localhost:3001/prep และดูว่ามี field token และ authorizationHeader
  • ใช้ค่า lab-token ใน header Authorization: Bearer lab-token เมื่อเรียก /protected
  • ทดสอบ 1 request เป็นหลัก แต่ถ้าต้องการดู concurrent behavior ให้ลอง 2-3 threads พร้อมกัน
  • ตรวจสอบ response ว่าได้ข้อความอนุญาตเข้าถึง resource
เฉลย

Response จาก /prep จะมี field token และ authorizationHeader ซึ่งค่า token ปกติคือ lab-token

เมื่อเรียก /protected พร้อม header ต่อไปนี้:

Authorization: Bearer lab-token

Response ที่ถูกต้องจะเป็น:

{
  "message": "protected resource access granted",
  "authenticated": true,
  "tokenSource": "authorization"
}

Task 4: ลอง auth แบบ JWT

โจทย์

ใช้ POST /auth/login โดยส่ง JSON body:

{
  "username": "demo",
  "password": "password"
}

แล้วนำ token ที่ได้ไปเรียก POST /auth/verify พร้อม header Authorization: Bearer <token>

วิธีทำ
  • ส่ง POST ไปที่ http://localhost:3001/auth/login พร้อม body ที่กำหนด
  • คัดลอกค่า token จาก response
  • ส่ง POST อีกครั้งไปที่ http://localhost:3001/auth/verify พร้อม header Authorization: Bearer <token>
  • ทดสอบด้วย 1-2 concurrent requests เพื่อตรวจสอบว่า token ยัง valid เมื่อใช้งานพร้อมกัน
  • ตรวจสอบ response ว่า valid: true และข้อมูล decoded ตรงตาม user
เฉลย

Response จาก /auth/login จะเป็น JSON ที่มี field token เช่น:

{
  "message": "login successful",
  "authenticated": true,
  "token": "eyJhbGciOiJIUzI1NiIs..."
}

เมื่อใช้ token นี้เรียก POST /auth/verify จะได้ response ประมาณ:

{
  "message": "token is valid",
  "valid": true,
  "decoded": {
    "userId": "user-123",
    "username": "demo",
    "iat": "...",
    "exp": "..."
  }
}

Task 5: ทดสอบ validation error

โจทย์

เรียก POST /submit-one โดยไม่ส่ง body หรือส่ง body ว่าง ๆ จากนั้นสังเกตว่าระบบตอบอย่างไร

วิธีทำ
  • ใช้ curl หรือ Postman ส่ง POST ไปที่ http://localhost:3001/submit-one โดยไม่ใส่ body
  • ใช้ 1-3 concurrent requests เพื่อยืนยันว่าการ validate ทำงานกับหลาย request ได้
  • ดูว่า response เป็น HTTP 400 หรือมี JSON error
  • ลองส่ง body ถูกต้อง เช่น { "name": "test" } แล้วเปรียบเทียบผล
เฉลย

Response จะเป็น HTTP 400 พร้อม JSON:

{
  "error": "missing_required_parameter",
  "required": ["name"]
}

ถ้าส่ง body ที่ถูกต้อง เช่น { "name": "test" } จะได้ response:

{
  "message": "received one required parameter",
  "data": { "name": "test" }
}

Task 6: ลอง I/O flow และ cleanup

โจทย์

เรียก GET /io?mode=write และ GET /io?mode=read จากนั้นเรียก POST /cleanup เพื่อลบไฟล์ชั่วคราว

วิธีทำ
  • เรียก GET http://localhost:3001/io?mode=write เพื่อสร้างไฟล์ชั่วคราว
  • เรียก GET http://localhost:3001/io?mode=read เพื่ออ่านข้อมูลจากไฟล์
  • สำหรับ I/O flow ให้ลอง 1-2 concurrent requests เพื่อดูพฤติกรรมแบบเรียงลำดับ
  • เรียก POST http://localhost:3001/cleanup เพื่อเคลียร์ไฟล์ทั้งหมด
  • ตรวจสอบ response แต่ละขั้นตอนว่าแสดง durationMs และสถานะการ cleanup
เฉลย

/io?mode=write และ /io?mode=read จะตอบ JSON ที่มี durationMs และ mode

หลังนั้น POST /cleanup จะตอบ JSON เช่น:

{
  "message": "cleanup completed",
  "cleaned": ["io-test.dat"],
  "cleanedCount": 1
}
ถ้าคุณทำครบทั้ง 6 ข้อแล้ว ให้ลองกลับไปอ่าน Demo Flow เพื่อเรียนรู้ flow ที่ซับซ้อนขึ้น และลองนำคำตอบที่ได้ไปออกแบบ JMeter test ของตัวเอง

Next-Level Exercises

Challenge 1: เปรียบเทียบ /fast กับ /slow

โจทย์

เรียก /fast และ /slow แล้วจดเวลาที่ใช้สำหรับแต่ละ request เปรียบเทียบความแตกต่าง

วิธีทำ
  • ใช้เครื่องมือวัดเวลาเช่น curl with time หรือ Postman เพื่อเรียกทั้งสอง endpoint
  • บันทึกค่า latency ของ /fast และ /slow
  • เทียบผลลัพธ์ว่าต่างกันเท่าไร และตรวจสอบว่าค่า delay ตรงตาม slowDelayMs
เฉลย

คุณจะเห็นว่า /slow ใช้เวลามากกว่า /fast เสมอ โดยเวลาเพิ่มขึ้นตาม config ของ slowDelayMs

Challenge 2: สร้าง error case ด้วย /submit-two

โจทย์

เรียก POST /submit-two โดยส่ง body ที่ขาด field type เท่านั้น แล้วดู response

วิธีทำ
  • ส่ง POST ไปที่ http://localhost:3001/submit-two พร้อม body เช่น { "name": "test" }
  • ลอง 1-3 concurrent requests เพื่อดูว่า validation error สม่ำเสมอ
  • ดู response code ว่าเป็น 400 และ response body ว่าแสดง error รายการที่ขาด
  • ลองส่ง body ครบทั้ง name และ type เพื่อเปรียบเทียบผลลัพธ์
เฉลย

Response จะเป็น HTTP 400 และ JSON จะมี:

{
  "error": "missing_required_parameters",
  "required": ["name", "type"]
}

Challenge 3: ทดสอบ token invalid

โจทย์

เรียก POST /auth/verify โดยส่ง header Authorization: Bearer invalid-token แล้วสังเกต response

วิธีทำ
  • ส่ง POST ไปที่ http://localhost:3001/auth/verify โดยกำหนด header Authorization: Bearer invalid-token
  • ทดลอง 1-2 requests เพื่อดูว่าการ invalid token ถูกตรวจสอบทุกครั้ง
  • ตรวจสอบ response code ว่าเป็น 403 และ response body ว่าแสดง error invalid token
  • ลองเปรียบเทียบกับ token ที่ได้จาก /auth/login เพื่อดูความแตกต่าง
เฉลย

Response จะเป็น HTTP 403 พร้อม JSON:

{
  "error": "invalid_token",
  "message": "Token is not valid"
}

Challenge 4: เมตริกพื้นฐาน

โจทย์

เรียก GET /metrics แล้วค้นหาตัวแปร http_request_duration_seconds_count หรือ metric อื่นที่เกี่ยวกับ HTTP request

วิธีทำ
  • เปิด GET http://localhost:3001/metrics ใน browser หรือ curl
  • ค้นหาสตริง http_request_duration_seconds_count หรือชื่อ metric ที่คล้ายกัน
  • ดูลักษณะว่าเป็น Prometheus counter/histogram และใช้สำหรับวัด request duration อย่างไร
เฉลย

คุณจะพบข้อความประเภท Prometheus ที่ประกอบด้วย metrics count และ histogram สำหรับ request duration เพื่อใช้ดูการ perform ของ API

Intermediate Assignment

Intermediate 1: วิเคราะห์ /status ในเชิง runtime

โจทย์

เรียก GET /status แล้วดูว่า activeRequests, uptimeSec, และ pid มีค่าอย่างไรเมื่อเรียกซ้ำหลายครั้ง

วิธีทำ
  • เรียก GET http://localhost:3001/status หลายครั้งในช่วงเวลาที่ต่างกัน
  • ลองทำซ้ำ 2-3 requests ในแต่ละรอบ เพื่อดูความคงที่ของค่า
  • จดค่าของ pid, uptimeSec และ activeRequests
  • สังเกตว่า pid ไม่เปลี่ยน, uptimeSec เพิ่มขึ้น และ activeRequests อาจเปลี่ยนตามโหลด
เฉลย

คุณจะเห็นว่า pid คงที่ตลอด session, uptimeSec เพิ่มขึ้นตามเวลา และ activeRequests จะเปลี่ยนตามจำนวนคำขอที่ระบบกำลังประมวลผล

Intermediate 2: เปรียบเทียบ /fast และ /slow โดยใช้ /status

โจทย์

เรียก GET /fast และ GET /slow พร้อมกัน แล้วเรียก GET /status เพื่อดูค่า activeRequests และการตอบสนองของ server

วิธีทำ
  • เปิดคำสั่งสองแท็บหรือสอง terminal: เรียก /fast และ /slow พร้อมกัน
  • เริ่มด้วย 1-3 concurrent requests สำหรับแต่ละ endpoint
  • เรียก GET /status ขณะนั้นและบันทึกค่า activeRequests กับ uptimeSec
  • สังเกตว่าระบบยังตอบได้แม้ /slow ใช้เวลานานขึ้น
เฉลย

ในขณะที่ /slow กำลังทำงาน, activeRequests อาจเพิ่มขึ้นและ uptimeSec ยังคงนับต่อไป คำสั่งนี้ช่วยให้เข้าใจว่าระบบยังทำงานอยู่ระหว่าง latency สูง

Intermediate 3: ตรวจสอบ error case ด้วย request rate

โจทย์

เรียก POST /submit-two โดยส่ง body ที่ขาด field type แล้วดู error response พร้อมสังเกตค่า response code และเมสเสจ

วิธีทำ
  • ส่งหลายคำขอไปยัง /submit-two โดยขาด type
  • เริ่มด้วย 5-10 concurrent invalid requests เพื่อสร้าง error rate เบื้องต้น
  • เช็ก response code ว่าเป็น 400 ทุกครั้งและ body แสดง field ที่ขาด
  • ถ้าทำได้ ลองส่งซ้ำหลายครั้งเพื่อตรวจสอบว่า error behavior สม่ำเสมอ
เฉลย

คุณจะได้ HTTP 400 และ JSON error พร้อม field missing_required_parameters ซึ่งแสดงว่าระบบตรวจจับ validation error ได้ถูกต้อง แม้ load เพิ่มขึ้น

Intermediate 4: หา histogram metric จาก /metrics

โจทย์

เรียก GET /metrics แล้วหา metric ที่เป็น counter หรือ histogramสำหรับ response duration เช่น http_request_duration_seconds_bucket

วิธีทำ
  • เรียก GET http://localhost:3001/metrics แล้วค้นหาชื่อ metric ที่มีคำว่า bucket หรือ count
  • ถ้าอยากเพิ่มข้อมูลให้ metrics ให้รัน 5-10 requests ก่อนแล้วดึง /metrics อีกครั้ง
  • สังเกตว่า histogram bucket มีค่า latency เป็นช่วง เช่น le="0.1", le="0.5"
  • เช็กว่า metrics นี้สามารถใช้คำนวณ percentile ได้
เฉลย

ถ้าพบ http_request_duration_seconds_bucket แปลว่า metrics นี้เก็บ histogram latency และสามารถใช้วิเคราะห์ percentile ได้

Advanced Assignment

Advanced 1: วัด SLA และเปรียบเทียบกับผลจริง

โจทย์

กำหนด SLA เช่น p95 < 200ms, Error rate < 1% แล้วเรียก GET /metrics หรือทดสอบหลายครั้งเพื่อดูว่าระบบผ่าน SLA หรือไม่

วิธีทำ
  • สร้าง load ประมาณ 10-20 requests หรือ 2-5 concurrent threads เพื่อให้เห็น metric ได้ชัด
  • เรียก GET /metrics ก่อนและหลังรัน request หลายครั้ง
  • หา metric ที่แสดง histogram และ error count
  • เปรียบเทียบค่า percentile กับ SLA ที่กำหนด เช่น คำนวณ p95 จาก bucket
  • ดูว่าค่า error rate ต่ำกว่า 1% หรือไม่
เฉลย

ดูค่า percentile จาก metric histogram และ error count ถ้า p95 สูงกว่าค่า SLA หรือ Error rate เกิน 1% แปลว่าต้องปรับ tuning หรือแก้ bottleneck

Advanced 2: ทดสอบ recovery หลังโหลดสูง

โจทย์

เรียก /slow ซ้ำหลายครั้งเพื่อเพิ่ม load แล้วจดค่า activeRequests พร้อมดูว่า /status กลับมาปกติเมื่อหยุดร้องขอหรือไม่

วิธีทำ
  • ส่งคำขอซ้ำ ๆ 10-20 requests ไปที่ /slow หรือใช้ 3-5 concurrent threads
  • ตรวจสอบ /status ระหว่างโหลดสูงเพื่อดูค่า activeRequests
  • หยุดส่ง request แล้วเรียก /status อีกครั้งเพื่อดูว่า activeRequests ลดลงและ server ยัง responsive
เฉลย

คุณควรเห็นว่าหลังหยุด /slow, activeRequests ลดลง และ server ยังตอบกลับ /status ได้ตามปกติ แสดงว่าระบบ recovery ได้

Advanced 3: เช็ก token expiration / invalidation

โจทย์

ใช้ POST /auth/login รับ token แล้วเรียก POST /auth/verify พร้อม token เดิมหลังรอเวลาสั้น ๆ เพื่อดูการ validate token

วิธีทำ
  • ส่ง POST ไปที่ /auth/login เพื่อรับ token
  • ใช้ token เดิมเรียก /auth/verify พร้อม header Authorization: Bearer <token>
  • หากต้องการทดสอบ expiration ให้รอ 10-30 วินาทีแล้วลองเรียกอีกครั้ง
  • ถ้าต้องการดู concurrency ให้ทดลอง 2-3 verify requests พร้อมกัน
เฉลย

ถ้า token ยังถูกต้อง คุณจะได้ valid: true แต่ถ้าระบบตั้งค่า token expiration ไว้ใกล้เคียง อาจพบ invalid_token เมื่อหมดอายุ

Advanced 4: สร้างและวิเคราะห์ error spike

โจทย์

เรียก POST /submit-two หรือ /error หลายครั้งเพื่อทำให้ error rate สูงขึ้น จากนั้นดูว่า /metrics และ /status ว่า error rate และ activeRequests เปลี่ยนอย่างไร

วิธีทำ
  • เรียก POST /submit-two หรือ /error 10-20 ครั้งหรือใช้ 5-10 concurrent invalid requests
  • เรียก GET /metrics เพื่อตรวจสอบ error count และ metric ที่เกี่ยวข้อง
  • เรียก GET /status เพื่อตรวจสอบว่าระบบยังตอบได้และ activeRequests เปลี่ยนอย่างไร
เฉลย

คุณควรเห็น error count เพิ่มขึ้นใน metrics และถ้า error rate สูงเกิน SLA อาจทำให้ service reliability ลดลง แม้ uptime ยังสูง

Performance Testing Assignments

Load Testing: ทดสอบโหลดปกติ

โจทย์

สร้าง JMeter test plan เพื่อเรียก GET /fast และ GET /slow ภายใต้โหลดปกติ (expected load) แล้ววิเคราะห์ throughput, latency, และ error rate

วิธีทำ
  • สร้าง Thread Group ใน JMeter ด้วย 10-20 threads, ramp-up 30 วินาที, loop count 5-10 ครั้ง
  • เพิ่ม HTTP Request samplers สำหรับ /fast และ /slow
  • เพิ่ม Response Assertion เพื่อเช็ก response code 200 และ message ที่ถูกต้อง
  • เพิ่ม Aggregate Report listener เพื่อดู average response time, throughput, และ error %
  • รัน test แล้วเรียก GET /status และ GET /metrics เพื่อดู activeRequests และ histogram metrics
เฉลย

Load testing ควรแสดง throughput สม่ำเสมอ, latency ต่ำกว่า SLA (เช่น p95 < 500ms), และ error rate < 1%. ถ้า throughput ลดลงหรือ latency เพิ่มขึ้น แสดงว่ามี bottleneck

Stress Testing: ทดสอบขีดจำกัด

โจทย์

เพิ่มโหลดอย่างต่อเนื่องจนถึงจุดที่ระบบเริ่มล้มเหลว (breaking point) โดยเรียก GET /slow และ POST /submit-one แล้วสังเกตเมื่อ error rate เพิ่มขึ้นหรือ response time ช้าลง

วิธีทำ
  • เริ่มด้วย Thread Group 20-50 threads, ramp-up 60 วินาที, duration 5-10 นาที
  • เพิ่ม HTTP Request สำหรับ /slow และ /submit-one พร้อม body ที่ถูกต้อง
  • ใช้ Constant Timer 1-2 วินาทีระหว่าง requests เพื่อจำลอง user pacing
  • เพิ่ม listeners เช่น View Results Tree และ Summary Report เพื่อดู error trends
  • รัน test แล้ว monitor /status ทุก 30 วินาทีเพื่อดู activeRequests และ uptime
เฉลย

Stress testing จะพบ breaking point เมื่อ error rate > 5%, response time > 2-3 วินาที, หรือ server ไม่ตอบสนอง. จุดนี้แสดง maximum capacity ของระบบ

Spike Testing: ทดสอบโหลดแบบกระตุก

โจทย์

จำลองการเพิ่มโหลดแบบฉับพลัน (spike) โดยเรียก GET /fast และ GET /slow พร้อมกันจำนวนมากในช่วงสั้น ๆ แล้วดูว่าระบบ recovery ได้หรือไม่

วิธีทำ
  • สร้าง Thread Group ด้วย 50-100 threads, ramp-up 10 วินาที (เร็วมาก), loop count 1-2 ครั้ง
  • เพิ่ม HTTP Request สำหรับ /fast และ /slow
  • ใช้ Ultimate Thread Group หรือ Step-Up Thread Group เพื่อสร้าง spike pattern
  • เพิ่ม listeners เพื่อดู response time และ error rate ในช่วง spike
  • หลังรัน spike แล้วเรียก /status และ /metrics เพื่อดู recovery และ error metrics
เฉลย

Spike testing ควรแสดง latency เพิ่มขึ้นชั่วคราวในช่วง spike แต่ระบบควร recovery หลังโหลดลดลง. ถ้า error rate สูงหรือ server crash แสดงว่าต้องปรับ auto-scaling หรือ resource allocation

Endurance Testing: ทดสอบระยะยาว

โจทย์

รัน test ต่อเนื่องเป็นเวลานาน (hours) ภายใต้โหลดปกติเพื่อตรวจสอบ memory leaks, resource exhaustion, หรือ degradation ใน performance

วิธีทำ
  • ตั้ง Thread Group 5-15 threads, ramp-up 30 วินาที, duration 30-60 นาที หรือยาวกว่านั้น
  • เพิ่ม HTTP Request สำหรับ /fast, /slow, และ /status (เพื่อ monitor ด้วย)
  • เพิ่ม Response Assertion และ listeners เพื่อ track performance trends
  • รัน test แล้ว monitor /status และ /metrics เป็นระยะเพื่อดู uptime, activeRequests, และ memory usage
  • สังเกตว่ามี degradation ใน response time หรือ error rate เมื่อเวลาผ่านไป
เฉลย

Endurance testing จะเปิดเผย issues เช่น memory leaks ถ้า response time เพิ่มขึ้นหรือ error rate สูงขึ้นเมื่อเวลาผ่านไป. ระบบที่ดีควร maintain performance สม่ำเสมอตลอด duration

Volume Testing: ทดสอบปริมาณข้อมูลขนาดใหญ่

โจทย์

ทดสอบระบบด้วยปริมาณข้อมูลขนาดใหญ่ เช่น ส่ง request ที่มี body ขนาดใหญ่ หรือเรียก endpoints ที่เกี่ยวข้องกับการประมวลผลข้อมูลจำนวนมาก แล้วดูว่า latency และ throughput เปลี่ยนแปลงอย่างไร

วิธีทำ
  • สร้าง Thread Group 5-10 threads, ramp-up 20 วินาที, loop count 3-5 ครั้ง
  • เพิ่ม HTTP Request สำหรับ POST /submit-one หรือ /submit-two พร้อมส่ง body ขนาดใหญ่ (เช่น JSON กับ array ขนาด 1000 elements หรือ string ยาว)
  • ใช้ CSV Data Set Config เพื่อ feed ข้อมูลขนาดใหญ่จากไฟล์
  • เพิ่ม listeners เพื่อดู response time และ error rate เมื่อ deal กับ large payloads
  • รัน test แล้ว monitor /status เพื่อดู activeRequests และ /metrics เพื่อดู memory หรือ CPU metrics ถ้ามี
เฉลย

Volume testing จะแสดงว่าละระบบ handle large data ได้ดีหรือไม่. ถ้า response time เพิ่มขึ้นอย่างมากหรือ error rate สูง แสดงว่าต้อง optimize data processing หรือ increase resource limits

Scalability Testing: ทดสอบการขยายตัว

โจทย์

ทดสอบว่าประสิทธิภาพของระบบเปลี่ยนแปลงอย่างไรเมื่อเพิ่มจำนวน users หรือ resources อย่างค่อยเป็นค่อยไป แล้วหาจุดที่ performance ไม่ scale ตาม

วิธีทำ
  • ใช้ Step-Up Thread Group หรือ Ultimate Thread Group เพื่อเพิ่ม threads ทีละขั้น (เช่น เริ่ม 5 threads, เพิ่มเป็น 10, 20, 50)
  • ตั้ง duration 2-5 นาทีต่อขั้นเพื่อให้ระบบ stabilize
  • เพิ่ม HTTP Request สำหรับ /fast และ /slow รวมถึง /status เพื่อ monitor
  • เพิ่ม Aggregate Report เพื่อดู throughput และ response time ที่แต่ละ level
  • วิเคราะห์ว่า throughput เพิ่มตามจำนวน threads หรือไม่ และหาจุดที่ performance plateau หรือลดลง
เฉลย

Scalability testing จะบอกว่าละระบบ scale ได้ดีหรือไม่. ถ้า throughput ไม่เพิ่มตาม users แสดงว่ามี bottleneck ใน architecture หรือ resources ไม่เพียงพอ
