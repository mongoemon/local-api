การตั้งค่าเซิร์ฟเวอร์

การเปลี่ยนแปลงทั้งหมดมีผลทันที — ไม่ต้องรีสตาร์ทเซิร์ฟเวอร์ ใช้ปุ่ม Preset เพื่อสลับระหว่างค่าเริ่มต้นปกติกับโหมด Stress หรือปรับค่าแต่ละตัวสำหรับการทดสอบเฉพาะจุด
Preset ด่วน:

การจำกัดอัตราคำขอ (Rate Limiting)

จำกัดจำนวนคำขอที่ client แต่ละรายสามารถส่งได้ภายในช่วงเวลาที่กำหนด หากเกินจำนวนที่อนุญาตจะได้รับ 429 Too Many Requests ปิดไว้เป็นค่าเริ่มต้นเพื่อไม่ให้กระทบการใช้งานปกติ เปิดเมื่อต้องการสังเกตพฤติกรรมการจัดการ error ระหว่าง load test
การตั้งค่า ค่า ควบคุมอะไร
เปิดใช้งาน
RATE_LIMIT_ENABLED
ค่าเริ่มต้น: ปิด
 เมื่อ เปิด ทุก request จะถูกนับต่อ IP ของ client ภายในช่วง window request ที่เกินจำนวน สูงสุดต่อ Window จะได้รับ 429 จนกว่า window จะรีเซ็ต
เปิด: เริ่มบังคับใช้ rate limit — JMeter จะได้รับ 429 เมื่อ threads × loops เกินจำนวนที่กำหนด
ปิด: ไม่มีการจำกัด request ไม่ว่าจะส่งมามากแค่ไหน
ระยะเวลา Window
RATE_LIMIT_WINDOW_MS
ค่าเริ่มต้น: 60000 ms (1 นาที)
มิลลิวินาที
 ระยะเวลาของ window หนึ่งรอบ หลังครบกำหนดนับ request ของแต่ละ IP จะรีเซ็ต
นานขึ้น: client ถูก rate limit นานขึ้นหลังชน cap — ฟื้นตัวยากขึ้น
สั้นลง: window รีเซ็ตเร็วขึ้น — rate limit หายเร็วหลังถูกเปิดใช้
สูงสุดต่อ Window
RATE_LIMIT_MAX
ค่าเริ่มต้น: 10000
คำขอต่อ window
 จำนวน request สูงสุดที่ client IP หนึ่งรายทำได้ใน window เดียวก่อนได้รับ 429 ค่าเริ่มต้น 10000 สูงมากจนแทบไม่มีผลสำหรับการทดสอบในเครื่อง
ต่ำ (เช่น 30–100): เกิด 429 เร็ว — เหมาะสำหรับสังเกตพฤติกรรม error handling ใน JMeter report
สูง: แทบไม่มีทางชน cap — rate limiting เปิดอยู่แต่ไม่รบกวนการทดสอบ

การรองรับพร้อมกัน (Concurrency)

กำหนดจำนวน request สูงสุดที่ประมวลผลพร้อมกันได้ในขณะเดียวกัน เมื่อถึงเพดาน request ใหม่ทุกอันจะได้รับ 503 Service Unavailable ทันที จำลองสภาวะที่เซิร์ฟเวอร์ยุ่งเกินไปจนไม่รับงานเพิ่ม
การตั้งค่า ค่า ควบคุมอะไร
คำขอพร้อมกันสูงสุด
MAX_CONCURRENT
ค่าเริ่มต้น: 50
คำขอพร้อมกัน
 จำนวน request สูงสุดที่ประมวลผลพร้อมกันในขณะใดขณะหนึ่ง request ที่เข้ามาขณะ cap เต็มจะได้รับ 503 ทันที เมื่อ response เสร็จ ตัวนับจะลดลงเอง
ต่ำ (เช่น 5–10): เกิด 503 เร็วเมื่อ JMeter threads เกิน cap — เหมาะสำหรับทดสอบ error handling และ retry logic
สูง: ทำให้ cap ยากขึ้นที่จะถึง — เหมาะสำหรับ load test โดยไม่ต้องการ 503 noise
ตั้งค่าต่ำกว่า 3 อาจทำให้หน้า Config นี้เข้าไม่ได้ขณะ load test รันอยู่ endpoint /api/config เข้าได้เสมอและสามารถใช้กู้คืนผ่าน curl ได้

Endpoint จำลองภาระงาน (Workload Endpoints)

ควบคุมพฤติกรรมจำลองของ /slow, /busy, /cpu, /memory, และ /io การเปลี่ยนแปลงมีผลกับ คำขอถัดไป ทันที ไม่ต้องรีสตาร์ท
การตั้งค่า ค่า ควบคุมอะไร
/slow — หน่วงเวลา
SLOW_DELAY_MS
ค่าเริ่มต้น: 200 ms
มิลลิวินาที
 เวลาที่ GET /slow รอก่อนตอบกลับ จำลองการเรียก database ที่ช้าหรือ I/O-bound operation การหน่วงเวลาเป็น async (non-blocking) จึงไม่กระทบ request อื่นที่รันพร้อมกัน
สูง (เช่น 1000–2000 ms): เพิ่ม p95/p99 โดยตรง — สังเกตได้ชัดใน Aggregate Report ของ JMeter
0 ms: /slow ตอบเร็วเหมือน /fast — ใช้เพื่อ isolate bottleneck อื่น
/busy — หน่วงเวลา
BUSY_DELAY_MS
ค่าเริ่มต้น: 3000 ms
มิลลิวินาที
 เวลาที่ GET /busy รอก่อนตอบกลับ จำลอง background job หนัก เช่น การสร้างรายงานหรือเรียก external API การหน่วงเวลานานทำให้ request สะสม — ใช้ร่วมกับ Max Concurrent ต่ำเพื่อสร้างแรงกดดัน 503 อย่างต่อเนื่อง
สูง (เช่น 8000–15000 ms): request ที่ active เต็ม concurrency cap เร็ว ทำให้เกิด 503 แม้มี JMeter threads ไม่มาก
0 ms: ลบ bottleneck นี้ — ใช้เมื่อต้องการทดสอบส่วนอื่น
/cpu — จำนวนรอบ
CPU_ITERATIONS
ค่าเริ่มต้น: 10,000,000
รอบการวนซ้ำ
 จำนวนรอบของ CPU loop แบบ synchronous ที่ GET /cpu รัน สิ่งนี้ บล็อก event loop ของ Node.js ขณะรัน — request อื่นทั้งหมดหยุดรอจนกว่าจะเสร็จ ที่ 10M รอบคาดว่าใช้เวลาประมาณ 20–50 ms บน hardware ทั่วไป
สูง (เช่น 50M–100M): บล็อก event loop 100–500 ms — latency ของทุก endpoint เพิ่มขึ้นขณะมี /cpu load พร้อมกัน
1000: แทบทันที — ลบ CPU bottleneck โดยไม่ต้องเปลี่ยน route
/memory — ขนาด Array
MEMORY_ARRAY_SIZE
ค่าเริ่มต้น: 1,000,000
จำนวน element
 จำนวน element ที่จัดสรรและเติมข้อมูลระหว่าง request แต่ละครั้งของ GET /memory Array จะถูกทิ้งหลังส่ง response สร้างแรงกดดันต่อ garbage collector ภายใต้ load ที่ค่าเริ่มต้น 1M elements แต่ละ request จัดสรรหน่วยความจำประมาณ 4–8 MB
สูง (เช่น 5M–10M): 20–80 MB ต่อ request — GC pause เริ่มเห็นได้ชัดและ latency ล่องลอยขึ้นภายใต้ load พร้อมกัน
1000: จัดสรรน้อยมาก — ลบแรงกดดัน memory สำหรับการทดสอบแบบ isolation
/io — ขนาดไฟล์
IO_FILE_SIZE_KB
ค่าเริ่มต้น: 1024 KB
กิโลไบต์
 ขนาดของไฟล์ที่ GET /io เขียนหรืออ่าน (เก็บที่ tmp/io-test.dat) I/O เป็น async จึงไม่บล็อก event loop แต่การอิ่มตัวของ disk throughput เพิ่ม latency ภายใต้ load พร้อมกัน
สูง (เช่น 10 MB–50 MB): ระยะเวลา I/O เพิ่มขึ้น — disk saturation เห็นได้ใน JMeter เมื่อหลาย thread กด /io พร้อมกัน
10 KB: แทบทันที — ลบ I/O latency โดยไม่ปิด route
