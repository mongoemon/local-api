Test Types And Thread Groups

หน้านี้สอนวิธีเลือก test type, จับคู่กับ thread group, ตั้งค่าให้ถูก, และอ่านผลให้ตรงกับ SLA ที่ลูกค้าต้องการ

Step 1: เลือก Test Type ให้ตรงกับ SLA

ก่อนรัน test ต้องรู้ก่อนว่า SLA พูดถึงอะไร เพราะ test type แต่ละแบบตอบคำถามต่างกัน
Test Typeใช้เมื่อ SLA พูดถึงคำถามที่ตอบได้ตัวอย่างเกณฑ์
Load Test traffic ปกติ, expected users, baseline performance ระบบผ่าน SLA ภายใต้ load จริงหรือไม่ p95 < 800ms ที่ 20 users
Stress Test capacity, breaking point, graceful degradation ระบบเริ่ม degrade หรือ fail ที่ level ไหน ยังตอบได้จนถึง 80 concurrent users
Spike Test traffic surge, flash sale, peak event, recovery time ระบบรับ load พุ่งเร็ว และ recover กลับภายในกี่วินาที traffic 3x ภายใน 1 นาที, recover ใน 2 นาที
Endurance Test stability, continuous operation, memory drift SLA ยังนิ่งหรือ drift เมื่อรันหลายชั่วโมง p95 < 900ms ตลอด 8 ชั่วโมง

Step 2: เลือก Thread Group ให้เหมาะกับ Test Type

Thread Groupเหมาะกับ Test Typeควบคุมอะไรเลือกเมื่อ
Normal Load, Endurance จำนวน threads, ramp-up, loop count เริ่มต้น, functional check, baseline, load ธรรมดา
Concurrency Stress, Spike, Load จำนวน concurrent users ที่ active พร้อมกัน อยากรู้ว่าระบบรองรับกี่ sessions พร้อมกัน
Stepping Stress, Spike เพิ่ม threads เป็นขั้น ๆ ทีละช่วง อยากหา breaking point หรือดู degradation เป็น step
Arrival Rate Load, Endurance request rate ต่อวินาที (RPS/TPS) อยากคุม throughput rate ไม่ใช่ user count

Step 3: JMeter Thread Group Configuration Cheat Sheet

ค่าด้านล่างนี้เป็นจุดเริ่มต้น ปรับได้ตามโหลดที่ลูกค้าระบุ

Normal Thread Group — Load Test

Thread Group
  Number of Threads (users):  10–20
  Ramp-Up Period (seconds):   30
  Loop Count:                 20
  Duration (seconds):         — (ใช้ loop count แทน)

ใช้กับ: baseline, functional load, load test พื้นฐาน

Concurrency Thread Group — Stress Test

Concurrency Thread Group (requires bzm plugin)
  Target Concurrency:   เริ่ม 10, เพิ่มถึง 80+
  Ramp-Up Time (sec):   60
  Ramp-Up Steps:        5
  Hold Target Rate:     120 วินาที

ใช้กับ: stress test, หา saturation point, เช็ก active sessions

Stepping Thread Group — Spike / Threshold

Stepping Thread Group (requires plugin)
  Start Threads Count:       5
  Initial Delay (sec):       0
  Start users count:         5
  Start users period (sec):  30
  End Threads Count:         100

ใช้กับ: spike test, หา breaking point แบบ step-by-step

Arrival Rate Thread Group — Steady Traffic

Arrivals Thread Group (requires bzm plugin)
  Target Rate (requests/sec): 50
  Ramp-Up Time (sec):         30
  Ramp-Up Steps:              3
  Hold Target Rate (sec):     120

ใช้กับ: คุม RPS, open workload simulation, endurance ที่ rate คงที่

Step 4: Test Type Structures ใน JMeter

Load Test

Thread Group (Normal หรือ Concurrency หรือ Arrival)
└─ Transaction Controller - Browse Flow
   ├─ HTTP Request - demo context
   ├─ HTTP Request - demo dashboard
   ├─ HTTP Request - demo search
   └─ HTTP Request - product details
└─ Throughput Controller - Cart Flow (40%)
   └─ Transaction Controller - Add And Checkout
      ├─ HTTP Request - add to cart
      └─ HTTP Request - checkout
└─ If Controller - if demoOrderId exists
   └─ HTTP Request - order status
└─ Aggregate Report

Stress Test

Concurrency Thread Group
└─ Transaction Controller หรือ endpoint หลัก
   ├─ HTTP Request - target endpoint
   └─ JSON Extractor (ถ้าต้องการ)
└─ Summary Report
└─ Aggregate Report

Spike Test

Stepping Thread Group หรือ Concurrency Thread Group
└─ target endpoint หรือ full transaction flow
└─ View Results Tree (เพื่อดู response ในช่วง spike)
└─ Aggregate Report

Endurance / Soak Test

Normal Thread Group หรือ Arrival Rate Thread Group
  — ตั้ง Duration หลายชั่วโมง แทนการใช้ Loop Count
└─ target endpoint หรือ demo flow
└─ Backend Listener (ส่ง metric ไป Grafana/InfluxDB ถ้ามี)
└─ Aggregate Report

Step 5: Test Matrix By Layer

ในการทดสอบจริง เราต้องวัดหลาย layer พร้อมกัน ไม่ใช่แค่ดู response time อย่างเดียว
Layerสิ่งที่ต้องทดสอบเครื่องมือเหมาะกับ Test Type
Application endpoint response time, error rate, transaction flow JMeter Aggregate Report, Summary Report Load, Stress, Spike, Endurance
Runtime activeRequests, uptime, PID stability, Prometheus metrics GET /status, GET /metrics Load, Endurance — ดูระหว่างรัน
Infrastructure CPU, memory, disk I/O, network GET /cpu, GET /memory, GET /io, OS tools Stress, Endurance — ดูพร้อมกับ app layer
Reliability recovery time, error pattern, graceful degradation View Results Tree, Backend Listener Spike, Stress

Step 6: Metrics Layers — อ่านจากที่ไหน

Metricอ่านจากใช้วัดอะไร
Response time, p90/p95/p99 JMeter Aggregate Report latency ของแต่ละ endpoint และ flow รวม
Error rate JMeter Summary/Aggregate Report % ของ request ที่ fail (4xx, 5xx, timeout, assertion fail)
Throughput (RPS/TPS) JMeter Aggregate Report จำนวน request ที่ระบบตอบสำเร็จต่อวินาที
Active requests GET /status → activeRequests จำนวน request ที่กำลัง process พร้อมกัน
Uptime, PID GET /status ยืนยันว่า server ไม่ crash และยังเป็น process เดิม
HTTP request histogram GET /metrics latency distribution แบบ Prometheus bucket
CPU / Memory GET /cpu, GET /memory ดู compute load ระหว่างทดสอบ

Step 7: Suggested Run Order สำหรับผู้เริ่มต้น

รอบที่ 1 — Baseline (1 user)

ยืนยันว่า flow ทำงานถูกต้องก่อนเพิ่ม load ใด ๆ

  • 1 thread, 1 loop, ไม่มี ramp-up
  • เปิด View Results Tree เพื่อดู request/response จริง
  • ต้องได้ 200 ทุก step และ variable chain ถูกต้อง
  • ถ้า error ให้แก้ก่อน — ไม่รันรอบต่อไปจนกว่า baseline จะผ่าน

รอบที่ 2 — Load Test (expected load)

ทดสอบที่โหลดปกติตามที่ลูกค้าระบุ เพื่อยืนยัน SLA หลัก

  • Normal Thread Group: 10–20 threads, ramp-up 30s, loop 20
  • เปิด Aggregate Report เพื่อดู p90/p95/p99
  • เปรียบกับ SLA: p95, error rate, traffic mix
  • ถ้าผ่าน → ไป stress test; ถ้าไม่ผ่าน → ดู bottleneck ก่อน

รอบที่ 3 — Stress Test (push to limit)

หาจุดที่ระบบเริ่ม degrade โดยเพิ่ม load เรื่อย ๆ

  • Concurrency Thread Group: เพิ่มจาก 20 → 40 → 80 → 120 users
  • ดู error rate และ p95 ที่แต่ละ step
  • บันทึกจุดที่ error เริ่มขึ้น หรือ latency breach SLA
  • นั่นคือ breaking point / capacity threshold

รอบที่ 4 — Spike Test (burst)

จำลองการขึ้น load แบบฉับพลัน เพื่อดู recovery

  • Stepping Thread Group: พุ่งจาก 5 → 100 threads ใน 30 วินาที
  • ดู error burst และ recovery time หลัง spike ลง
  • ถ้าลูกค้าระบุ "ต้อง recover ใน 2 นาที" ให้ดูที่ timestamp

รอบที่ 5 — Endurance Test (long run)

รันที่ expected load นาน ๆ เพื่อดู drift และ memory behavior

  • Normal Thread Group: 10 threads, duration 1–8 ชั่วโมง
  • ดู p95 ต้นรอบ vs ท้ายรอบ — ถ้าเพิ่มขึ้นเรื่อย ๆ = leak
  • เปิด GET /status และ GET /metrics ดูค่า runtime ระหว่างรัน

Quick Reference: Test Type → Thread Group → SLA Metric

Test TypeRecommended Thread GroupPrimary Metric To CheckPass Condition Example
Load Normal หรือ Arrival Rate p95, error rate, traffic mix p95 < 800ms, error < 1%
Stress Concurrency หรือ Stepping จุดที่ error เริ่มขึ้น, p95 breach level ระบบยัง stable ที่ 80 users
Spike Stepping หรือ Concurrency error burst size, recovery time recover ใน 2 นาทีหลัง spike
Endurance Normal หรือ Arrival Rate + Duration p95 drift ต้นรอบ vs ท้ายรอบ p95 < 900ms ตลอด 8 ชั่วโมง

Quick Guidance

  • เริ่มจาก Normal Thread Group เสมอ ถ้าเพิ่งเริ่มต้นหรือต้องการ baseline
  • ถ้าจะหา concurrent user limit ให้ใช้ Concurrency Thread Group
  • ถ้าจะหา breaking point เป็นขั้น ให้ใช้ Stepping Thread Group
  • ถ้าจะคุม request rate (RPS) ให้ใช้ Arrival Rate Thread Group
  • ก่อนดู latency ให้ดู Error % ก่อนเสมอ — ถ้า error สูงอยู่ latency ไม่มีความหมาย
  • ดู p95 ใน Aggregate Report เป็นหลัก ไม่ใช่ Average
  • ดู parent sample ของ Transaction Controller สำหรับ SLA แบบ user journey
  • เปิด GET /status ระหว่างรัน เพื่อดู activeRequests และยืนยัน server ไม่ crash
