Performance Testing Glossary

หน้านี้รวบรวมคำศัพท์ที่เจอบ่อยในการทำ performance testing พร้อมคำอธิบายภาษาไทยและตัวอย่างสั้น ๆ
คำศัพท์ ความหมาย
Throughput จำนวน request ที่ระบบตอบกลับสำเร็จในช่วงเวลาหนึ่ง หน่วยมักเป็น requests per second (RPS) หรือ transactions per second (TPS)
นับเป็น request / transaction ที่เสร็จสมบูรณ์ ไม่ใช่จำนวนขั้นตอนหรือ process ภายในระบบ
ตัวอย่าง:
  • ถ้า throughput = 120 RPS แปลว่าในหนึ่งวินาทีระบบตอบกลับคำขอสำเร็จ 120 ครั้ง
  • ถ้า API ต้องทำ 3 ขั้นตอน (เช่น อ่าน DB, เขียน log, ส่ง response) แต่สำเร็จครบทั้งคำขอเดียว นับเป็น 1 request ไม่ใช่ 3
  • ถ้าใน 10 วินาที ระบบตอบกลับคำขอสำเร็จ 900 ครั้ง จะมี throughput = 90 RPS
Latency เวลาที่ใช้ในการตอบสนองจากจุดเริ่มต้นของ request จนกระทั่งเริ่มได้รับ response ส่วนมากดูเป็นค่า p50/p95/p99
Response Time เวลาทั้งหมดที่ระบบใช้ในการตอบ request ตั้งแต่รับจนเสร็จสมบูรณ์ มักวัดเป็นค่า median, p95, p99
Concurrency จำนวน request ที่กำลังประมวลผลพร้อมกันในระบบหรือใน thread group ณ เวลาเดียวกัน
Ramp-up เวลาที่ใช้เพิ่มจำนวนผู้ใช้งานหรือ request ให้ถึง target load อย่างค่อยเป็นค่อยไป เพื่อจำลองการขึ้น traffic
Ramp-down เวลาที่ใช้ในการลดจำนวนผู้ใช้งานหรือ request ลงหลังจบการทดสอบ เพื่อให้ระบบค่อย ๆ กลับสู่สถานะปกติ
Spike Test การเพิ่ม load แบบฉับพลันในระยะเวลาสั้น ๆ เพื่อดูว่าระบบตอบสนองและ recovery ได้อย่างไร
Stress Test ทดสอบจนระบบเกินความสามารถปกติ เพื่อดูจุดล้มเหลว, การจัดการ overload และ recovery behavior
Soak Test ทดสอบระบบด้วย load คงที่เป็นเวลานาน เพื่อตรวจสอบ memory leak, resource exhaustion และความเสถียรช่วงระยะยาว
Load Test ทดสอบระบบด้วย load ที่คาดว่าจะเกิดขึ้นจริง เพื่อยืนยันว่า SLA/SLO ถูกต้องตามความต้องการ
Bottleneck ส่วนของระบบที่เป็นคอขวดและจำกัด throughput หรือทำให้ latency สูง เช่น CPU, memory, disk I/O, database
SLA Service Level Agreement ข้อตกลงเชิงธุรกิจเกี่ยวกับระดับการให้บริการ เช่น p95 < 200ms หรือ availability 99.9%
SLO Service Level Objective คือเป้าหมายเชิงเทคนิคที่ตั้งขึ้นเพื่อตรงกับ SLA เช่น response time, error rate, availability
Error Rate เปอร์เซ็นต์ของ request ที่ล้มเหลวเมื่อเทียบกับ request ทั้งหมด เช่น 4xx / 5xx errors, timeout, หรือ assertion failure
ไม่ใช่ เพียงแต่ request ช้า หาก response เป็น 2xx และผ่าน assertion ถือว่าไม่ใช่ error
Time to First Byte (TTFB) Time to First Byte คือ เวลาที่ใช้จนระบบส่ง byte แรกกลับไปยัง client หลังจาก request ถูกส่งไป
Warm-up ช่วงเวลาที่ให้ระบบขึ้นสภาวะปกติก่อนเริ่มวัดจริง เช่น โหลด cache หรือเปิด connection pool
Think Time ระยะเวลาหยุดรอระหว่าง request ของผู้ใช้จำลอง เพื่อเลียนแบบพฤติกรรมผู้ใช้จริง
CPU Saturation สถานะที่ CPU ถูกใช้งานเต็มกำลังและไม่สามารถรองรับ request เพิ่มได้อีก
Uptime ระยะเวลาที่ระบบหรือบริการทำงานต่อเนื่องโดยไม่หยุดชะงัก เช่น server ทำงานได้ต่อเนื่อง 7 วัน จะมี uptime = 7 วัน
PID Process ID หมายเลขเฉพาะของ process ที่รันอยู่บนระบบปฏิบัติการ ใช้ในการตรวจสอบ process, เก็บ log หรือฆ่า process
Memory Leak ปัญหาที่ระบบไม่คืน memory กลับหลังใช้งาน ทำให้ memory usage เพิ่มขึ้นเรื่อย ๆ จนเกิด crash หรือ OOM
Throughput Ceiling ระดับสูงสุดของ throughput ที่ระบบสามารถทำได้ก่อนเริ่มมี error หรือ latency พุ่งขึ้น
p90 / p95 / p99 ค่าร้อยละของ response time ที่ระบบทำได้ โดย p90 หมายถึง 90% ของ request ใช้เวลาน้อยกว่าค่านี้, p95 หมายถึง 95% ของ request, p99 หมายถึง 99% ของ request
ตัวอย่าง: ถ้า p95 = 200ms แปลว่า 95% ของคำขอทั้งหมดตอบได้เร็วกว่า 200ms และ 5% แรกอาจช้ากว่า 200ms
Thread Group กลุ่มของผู้ใช้งานจำลองใน JMeter ซึ่งกำหนดจำนวน threads, ramp-up time, และ loop count
Sampler องค์ประกอบที่ส่ง request เช่น HTTP Request, JDBC Request, FTP Request เพื่อจำลองคำขอจริงที่ระบบจะเจอ
Listener ส่วนที่เก็บและแสดงผลลัพธ์การทดสอบ เช่น Aggregate Report, Summary Report, View Results Tree
Assertion คำสั่งตรวจสอบผลลัพธ์ เช่น เช็กว่า response code เป็น 200 หรือ body มีข้อความที่ต้องการ
Timer ใช้เพิ่ม delay ระหว่าง request เพื่อจำลองช่วงเวลารอของผู้ใช้จริง
Config Element ตั้งค่าทั่วไปเช่น HTTP Header Manager หรือ CSV Data Set Config เพื่อใช้ซ้ำในหลาย sampler
PreProcessor / PostProcessor สคริปต์หรือการปรับค่าก่อน/หลังส่ง request เช่น สกัด token หรือปรับข้อมูลจาก response

Metric SLA

ใน performance testing metric หลักที่ใช้เป็น SLA มีดังนี้:

  • p90 / p95 / p99 - percentile ของ response time
  • Error rate - เปอร์เซ็นต์ของ request ที่ล้มเหลว
  • Throughput - จำนวน request ต่อวินาทีที่ระบบรองรับ
  • Availability - เปอร์เซ็นต์เวลาที่ระบบพร้อมให้บริการ
  • CPU utilization - เปอร์เซ็นต์การใช้งาน CPU ในช่วงเทสต์
  • Memory usage - ปริมาณหน่วยความจำที่ระบบใช้งานระหว่างเทสต์
  • TTFB - เวลาในการส่ง byte แรกกลับไปยัง client

ตัวอย่าง SLA รูปแบบต่าง ๆ

Metric SLA ตัวอย่าง คำอธิบาย ตัวอย่างผลลัพธ์
p90 < 150ms 90% ของ request ต้องเสร็จภายในค่านี้ ผลลัพธ์ = 132ms → Pass
p95 < 200ms 95% ของ request ต้องเสร็จภายในค่านี้ ผลลัพธ์ = 215ms → Fail
p99 < 300ms 99% ของ request ต้องเสร็จภายในค่านี้ ผลลัพธ์ = 280ms → Pass
Error rate < 1% ไม่เกิน 1% ของ request ต้องล้มเหลว ผลลัพธ์ = 0.8% → Pass
Throughput >= 120 RPS ระบบต้องตอบได้อย่างน้อย 120 request ต่อวินาที ผลลัพธ์ = 145 RPS → Pass
Availability >= 99.9% ระบบต้องพร้อมให้บริการมากกว่า 99.9% ของเวลาเทสต์ ผลลัพธ์ = 99.95% → Pass
CPU utilization < 80% CPU ต้องไม่ใช้เต็มจนเกิด saturation ในช่วง test ผลลัพธ์ = 76% → Pass
Memory usage < 70% ของ available RAM ไม่ควรใช้ memory เกินระดับที่ทำให้เกิด GC หรือล้มเหลว ผลลัพธ์ = 55% → Pass
TTFB < 100ms เวลาไปยัง byte แรกต้องไม่ช้าเกินนี้ ผลลัพธ์ = 88ms → Pass

p90 / p95 / p99 ใน JMeter

ใน JMeter ค่า p90/p95/p99 จะเห็นได้จาก listener ประเภทเช่น Aggregate Report หรือ Summary Report ที่แสดง percentile values โดยตรง

  • Aggregate Report: มีคอลัมน์ 90%, 95%, 99% ให้ดู response time ที่ percentile นั้น
  • Summary Report: แสดงค่า 90%, 95%, 99% คล้ายกัน และเหมาะกับการดูภาพรวมการทดสอบ
  • View Results in Table: ใช้ดู response ของแต่ละ sample แต่ percentile ต้องดูจาก listener แบบรวม

ตัวอย่างการใช้งาน:

1) ใส่ Thread Group และ HTTP Request sampler
2) เพิ่ม Aggregate Report listener
3) รันเทสต์
4) ดูค่าในคอลัมน์ 90%, 95%, 99%

Common JMeter listeners

  • Aggregate Report - ดูสรุปค่าเฉลี่ย, median, percentiles, throughput, error rate
  • Summary Report - สรุปผลลัพธ์แบบเรียบง่าย เหมาะกับการดูภาพรวม
  • View Results in Table - ดูรายละเอียดแต่ละ sample แต่ไม่เหมาะกับการอ่าน percentile ยาว ๆ
  • View Results Tree - ใช้ตรวจสอบ request/response ทีละรายการ เมื่อ debug script หรือ assertion

วิธีอ่านผลจาก listener

  • ดู 90%, 95%, 99% ว่าตรงกับ SLA หรือไม่
  • ถ้า p95 fail แต่ p90 pass แปลว่ากลุ่ม request ที่ช้าที่สุด 5% กำลังสร้างปัญหา
  • ถ้า p99 สูงมากกว่าค่า SLA แปลว่า request ที่ช้าที่สุด 1% มีปัญหา และอาจเป็นจุดบกพร่องเฉพาะบางเส้นทาง
  • หาก Error rate > 1% แปลว่ามีคำขอล้มเหลวมากเกินไป แม้ latency จะยังดีอยู่
    JMeter นับเป็น error เมื่อ response code เป็น 4xx/5xx, เกิด timeout, หรือ assertion fail
    ไม่ใช่ error เมื่อ response สำเร็จ (2xx) แต่ latency สูงกว่าค่า SLA
  • ใช้ Throughput เพื่อดูว่ายังขยายโหลดได้อีกหรือไม่

ถ้า 95% สูงมากกว่าค่า SLA แปลว่า request ที่ช้าที่สุด 5% กำลังทำให้ผู้ใช้บางส่วนรับประสบการณ์ช้า และควรติดตาม bottleneck เพิ่มเติม

ตัวอย่างผลลัพธ์หลังรันเทสต์

สมมติเรามี SLA ดังนี้:

  • p90 < 150ms
  • p95 < 200ms
  • p99 < 300ms
  • Error rate < 1%
Metric ผลลัพธ์จริง สถานะ คำอธิบาย
p90 132ms Pass 90% ของ request ตอบได้เร็วกว่า 132ms
p95 215ms Fail ค่าต้องน้อยกว่า 200ms แต่ 5% ช้าที่สุดใช้เวลา 215ms
p99 280ms Pass 99% ของ request ตอบได้เร็วกว่า 280ms
Error rate 0.8% Pass ต่ำกว่าเกณฑ์ 1%

ตัวอย่างนี้แสดงว่า performance โดยรวมยังโอเค แต่ต้องมาดูสาเหตุของ request 5% ที่ช้าที่สุด (p95 fail)

JMeter listener เช่น Aggregate Report จะรายงานค่าเหล่านี้ในช่อง 90%, 95%, 99% และให้เราเปรียบเทียบกับ SLA ได้ทันที
